# Native file capabilities

Native dialogs establish session-only file authority. Renderer-supplied paths never establish grants. Project grants are owner-bound random identifiers, expire after five minutes and carry read or read/write access. Trusted host import adapters can issue read-only single-file grants with `importFile`; this method is not exposed to the renderer. Existing project folder selection and tool input/output dialogs remain the native acquisition routes.

Every grant acquisition and resolution inspects the volume root and each existing component, records device/inode/birth identity and compares the exact native real path. Symbolic links, junctions that resolve elsewhere, hardlinked files, special files, case aliases, network/device paths and Windows reserved names or trailing-dot/space aliases are rejected. Replacing a parent or selected object invalidates the grant. A changed project grant is revoked. New outputs require an existing inspected parent and cannot overwrite an existing file.

The main-only `translate` adapter resolves its grant before calling a trusted host converter and resolves and compares the inspected object again afterwards. It accepts only a normalized absolute POSIX result, without control characters, backslashes or double-leading slashes. The converter is a host function, never renderer code or a command string. Existing execution adapters continue to own their WSL and container path mappings; this adapter does not admit an additional runtime or shell command.

## Limits and deferred verification

Path inspection is not an operating-system handle-relative sandbox. A concurrent external process can still race a later path-based open after resolution. Consumers must resolve immediately before use, use exclusive creation for outputs and retain existing execution admission rules. Unrecognized reparse mechanisms that preserve both the native path and object identity need native handle-based inspection before any stronger claim is possible.

This implementation was prepared under the requested speed mode. Tests, static analysis, independent review, runtime interaction and screenshots were deliberately deferred. PH02-T03 acceptance remains unverified, including native Windows reparse/case behavior and asynchronous translation cases.

## Native broker source and packaging contract

The Win32 broker source is `native/file-broker/main.cpp`. Root build integration calls `scripts/build/native-file-broker.ps1 -OutputDirectory <owned build directory>` inside an initialized MSVC x64 developer environment with the Windows SDK. The helper emits `material-file-broker.exe` and a hash-bound `broker-manifest.json`; its `runtimeVerified` field is always false. No compiler bootstrap has been added. An unavailable compiler is a real build limitation, never permission to substitute a plain child process.

The host module `src/main/security/native-file-broker.cjs` accepts only host-owned payload manifests and a native grant resolver. It stages the hash-verified broker and explicitly inventoried decoder resources. Decoder arguments come from a compiled operation allowlist. Implemented pipe operations are ImageMagick PNG/JPEG/WebP and FFmpeg WAV/MP3/FLAC. Video, documents, archives and PDF operations are outside this broker's implemented operation set.

The broker holds every ancestor directory without delete sharing, opens the input without write/delete sharing and checks its originally granted volume serial/file index using native handle information. It opens the selected output with exclusive CREATE_NEW semantics, rejects reparse tags, hardlinks and exact-path case differences, and retains both data handles for the entire child lifetime. Failed output is marked for deletion through that same held handle. Main-process grants expose their stored integer identity without rounding through floating-point file indices.

The decoder runs in a newly created zero-capability AppContainer with the all-application-packages access opt-out. Only its staged code/resources receive explicit AppContainer read/execute ACLs. The selected input and output paths receive no AppContainer ACL grants. An explicit handle inheritance list passes only input, output and a null diagnostic sink. No shell, inherited user environment or diagnostic content is exposed. The Job Object permits one process, bounds memory to 256 MiB, CPU user time to 20 seconds, and wall time to 30 seconds. Output growth is polled every 20 ms against 128 MiB, so this is a termination threshold rather than a hard filesystem quota. Cancellation bytes or closure of the parent's control pipe terminate the owned job; broker process exit closes its kill-on-close job handle. Parent-side termination remains bounded.

The AppContainer profile is temporary and removed after process termination. Its operating-system-managed profile/registry behavior and platform resource access have not been exercised. The broker module's WeakSet identity establishes only that an object was produced by the trusted host factory. Neither this identity, a matching binary hash, a successful compilation nor the source mechanism establishes runtime isolation acceptance. Callers must retain unavailable/unverified external-adapter presentation until separately authorized runtime evidence exists.

No root build, native compilation, decoder execution, tests, static analysis, review or screenshots were run for this source contribution. Build-driver/resource integration is coordinated separately with the packaging owner. Actual packaging, native compiler availability, AppContainer creation, executable/DLL access under the low-privilege token, cancellation, every denial boundary and converter behavior remain unverified.
