# Internal ISO producer transaction

This unexposed coordinator is not wired to the scheduler, renderer or native WSL execution. It provides a testable transaction boundary for a future explicitly lease-aware adapter. Current ISO submission remains intent-only. No production, native cleanup or boot acceptance is established by these synthetic tests.

The coordinator holds source, output and project locks across preparation, production, independently inspected process cleanup and output capture. The lease is an object-identity capability retained in a private WeakMap. Adapters must validate it for the exact job, derive current native authority and checkpoint their owner before releasing mutation input. Ordinary build and lifecycle operations do not accept this lease; directly calling them while these locks are held must continue to fail busy checks. Never remove those checks to activate this coordinator.

Current input verification binds configuration, source and admitted project proof hashes. Preparation and capture must return the existing unbound lifecycle observations. Only a successful transaction can create a job-bound receipt. It records output bytes, SHA-256, identity and structural observations, and always retains `bootVerified: false`. Matching prior output identity, another job's observation, changed grant/configuration, cancellation and unknown cleanup prevent receipt creation.

Each job receives an exclusive private storage directory with append-only numbered records. Ownership and cleanup records are separate for each stage. Records are synchronized and hash-linked; the final immutable receipt is another exclusive record. Existing directories, including interrupted or partially written records, block replay. Failure leaves the records intact. The store provides no restart admission or automatic deletion. Recovery must independently validate complete records and inspect every saved owner before it can release a scheduler reservation. Windows directory-entry crash durability is not claimed because directory fsync is unavailable through this route.

Adapter integration remains required: atomic lease-aware execution and lifecycle entrypoints, durable scheduler reservations, typed stage recovery, native grant derivation, receipt validation on readback, and recovery UI for unresolved namespace evidence. A new runtime namespace is never stopped-process proof. Neither a synthetic adapter nor the dependency-injected ownership validator provides native authority by itself.

## Internal lifecycle bridge

`createLeasedWslIsoOutputLifecycle` now provides an internal preparation/capture bridge. It reuses the existing native admission, ownership checkpoint, namespace check and input-release transport. The transaction validator binds the object-identity lease to the exact execution service, job, grant, runtime, admitted receipt and three roots. Validation runs at admission and each existing authority recheck. The bridge borrows already-held locks and never removes them, including cancellation, revocation and unknown cleanup. It does not temporarily remove locks. Ordinary lifecycle calls keep their original busy checks and reject supplied lease options.

The bridge is not constructed by production code. Producer execution, scheduler and renderer remain disconnected. Mocked integration exercises both lifecycle stages under one transaction, rejects forged/cross-job and changed execution/grant/runtime/root contexts, blocks an ordinary competing lifecycle call between stages, withholds input on checkpoint revocation and retains borrowed locks after cancellation or unknown cleanup. These checks provide no live WSL or firmware acceptance and do not address producer ownership refinement.

## Internal producer bridge and ownership refinement

`createIsoWslProducer` is an unexposed adapter for the internal `ExecutionService.startIsoProducer` route. The route requires an admitted native WSL receipt and a matching transaction lease, reuses existing process launch, cancellation and authorization handshake, and borrows the transaction's locks without acquiring or releasing them. Ordinary `start()` strips internal validation options and retains its busy behavior. No scheduler or renderer constructs this adapter.

The dedicated owner tracker requires one initial reservation with null PID/start followed by exactly one precise PID/start receipt. Both retain the same owner token, distribution, boot identity and PID namespace. Duplicate, conflicting, reversed or incomplete refinement is rejected. The transaction journal preserves both accepted records. Only the precise owner is eligible for independent stopped-state inspection; a reservation never proves process absence. Type declarations distinguish reservation and precise owners.

The producer adapter awaits the returned handle's `completion`, keeps cancellation attached, preserves terminal non-success and independently reconciles the precise owner before reporting success. The transaction performs its own additional cleanup inspection. Mocked cases cover initial-only ownership, changed token/distribution/boot/namespace, duplicate/conflicting refinement, cancellation before refinement, terminal failure and unknown cleanup. Existing execution protocol fixtures retain separate coverage of authorization-before-input and cancellation; they do not establish native WSL acceptance of this internal route. Direct admitted-native producer execution remains unverified. Scheduler activation, durable recovery admission and current GUI ISO acceptance remain incomplete.

## Read-only historical recovery inspection

`readIsoTransaction` reads an existing private job directory without creating directories, modifying reservations, releasing locks or calling a runtime. The filesystem reader bounds the inventory to 64 consecutive exclusive regular files of at most 64 KiB each. It rejects links, missing sequence members, unexpected files, invalid UTF-8/JSON, duplicate keys, changed identities and content changes during its bounded reread. It also checks that the reservation observation remains stable.

The semantic reader verifies the hash chain and exact record schemas, job/grant/runtime/source/configuration bindings, stage order, all accepted owners, successful stage results, matching cleanup records, preparation identity and final output receipt. The writer now records each successful stage result explicitly, so stopped ownership is never substituted for a successful process result. Older journals lacking these records remain unverified. Producer reservation and precise ownership retain the validated refinement rules. Output structure and the final receipt must retain `bootVerified: false`.

`complete` requires a caller-supplied trusted final-record SHA-256 anchor and a matching consistent journal with no reservation for that job. A self-consistent hash chain alone cannot detect a complete malicious rewrite; deriving the anchor from the same untrusted readback defeats this check. This is historical receipt consistency, not new process-absence, current grant, current output-byte or boot proof. A valid unfinished prefix with its retained reservation returns `incomplete`; malformed, truncated, missing, unanchored or inconsistent evidence returns `unknown`. Neither result clears or adopts anything. A copied completed receipt cannot be accepted under another job, source/configuration, grant or runtime. Scheduler activation and recovery authorization remain separate unfinished work.

Both directory snapshots enumerate through the same bounded synchronous iterator. Each performs at most 65 reads, closes on excess or an iterator exception, and rejects an oversized inventory before opening any record on that pass. Preparation hashes require a primitive string in both the writer and semantic reader; array-to-string coercion cannot admit malformed preparation or dispatch a producer. These boundaries were reproduced with deterministic negative tests before repair. The existing native lifecycle transport already validates string hashes separately; these findings do not establish a native execution exploit.

## Unexposed host build composition

`createIsoHostBuildAdapter` composes the existing native current-input capture, admitted WSL grant verification, leased lifecycle transport, producer and anchored readback. It compares genuinely captured source/configuration against the queued intent at each transaction check and derives the project-proof hash from the same admitted native receipt. A digest never creates a grant. The factory also requires a live host authorization callback; it cannot infer consent from job metadata.

Before its first current-input helper, the adapter requires a durable pending recovery reference. It supplies a separate durable current-helper ownership callback before releasing that helper's proof input. The actual `captureWslBuildIntent` transport now awaits this callback and revalidates authority afterward, preserving its exact-owner cancellation and independent cleanup. A failed checkpoint or revoked grant withholds input. The host adapter persists the final record anchor before readback and returns success only after complete anchored ISO receipt verification, retaining `bootVerified: false`.

This is not production activation. The existing quarantine schema stores one replaceable process receipt per job and cannot retain the journal reference, anchor and multiple separate current-helper owners. The adapter's required durable hooks therefore have no production implementation yet. The transaction journal also begins after the initial current-input derivation; pending recovery metadata must retain that helper independently before its journal exists. Existing identity verification and cleanup-inspection commands launch bounded native observation processes without their own durable ownership records. Their actual lifecycle and recovery treatment require explicit review before scheduler activation; they are not silently claimed covered by the productive-owner journal. These gaps must be repaired or explicitly resolved, not substituted with hashes or process names. The operations service, ordinary non-ISO build path, scheduler and renderer are unchanged.

Mocked host-composition tests verify pending-reference ordering, current-owner checkpoint ordering, fresh-receipt/readback before success, failed producer preservation, forged admission, changed source, checkpoint failure and grant revocation. Focused current-input transport tests verify that ownership persistence settles before helper input. No live WSL, container, native installation or firmware producer was invoked for these tests.

## Authority across asynchronous boundaries

The current-input transport checks cancellation, grant-map identity, captured receipt identity and runtime/path/proof bindings synchronously before and after every awaited native identity probe. It checks again immediately before proof input and immediately before result admission. Deferred-probe regressions revoke the grant, replace its receipt or abort during each of the initial, handshake and final verification waits. No input or result can be admitted through that wait boundary.

Host composition validates and deeply snapshots the accepted job payload before its first await. It separately captures stable job identity, log callback and the original AbortSignal capability without cloning or freezing signal internals. Authorization, recovery reference persistence and every later stage use that same snapshot. Caller mutation while a pending-reference write is delayed cannot switch the queued source/configuration revision, job identity or cancellation capability. Accessor-bearing payload/context fields are rejected instead of executing them as identity lookups.

Native identity and cleanup commands are bounded read-only observers, separate from writer stages. Current-input identity probes use the process runner's 10-second default bound. Lifecycle identity probes explicitly use 10 seconds. WSL cleanup observation uses an inner 8-second timeout, one-second kill-after interval and a 10-second outer process bound. A normal successful observer completion is interpreted only through its exact validated response; failed or timed-out cleanup observation remains unknown. An observer timeout is never producer-absence proof. The current-input helper itself has a separate 14-second bound and its exact-owner termination helper has a five-second bound. These source limits are not claims that native execution was exercised by the synthetic regressions.

Snapshot traversal rejects excessive array length before copying any elements and accepts only dense arrays without additional properties. Its existing 5,000-node and 64-KiB serialized-byte budgets apply recursively. String values and keys are charged before serialization, including UTF-8 bytes, JSON escapes and punctuation, so many individually acceptable strings cannot evade the aggregate bound. Safe sentinel regressions reproduce the sparse-billionth-index and aggregate/escaped-string cases without serializing expanded content. Valid dense metadata and the original cancellation capability remain supported.

## Separate durable ISO recovery inventory

`createIsoRecoveryRecords` is an internal append-only companion inventory. It does not modify or migrate the legacy `runtime-recovery.json` schema. Each exclusive job directory begins with the exact job, workspace, native grant, runtime, journal key, source/configuration/project-proof bindings and ISO policy. All later records retain that identity through an ordered hash chain. The inventory uses the same bounded, exclusive-file reader as transaction readback and allows at most 64 records and 24 distinct current-helper owners. Files are created exclusively, synchronized and never replaced or truncated by this API. Existing or malformed directories block reuse.

Current-helper ownership is appended as a separate precise-owner record for each unique owner token. Cleanup is another separate record matching that complete owner. Duplicates, replacements, cross-job/grant/runtime/source replay and conflicting anchors are rejected. Unknown cleanup remains incomplete and cannot be overwritten with a later success through this API. A verified-stopped current-helper verdict requires the exact `owned-session-absent` reason; observer timeout never becomes writer absence.

Reference progression is pending, receipt-recorded and verified. The trusted final-record anchor is immutable once recorded. Verified progression requires a cleanup record for every current helper and actual complete anchored transaction readback. Reading verified recovery repeats that historical transaction check; missing or changed journal evidence returns unknown. Complete records do not grant execution, restore a native grant, release memory locks, clear the transaction reservation or authorize retry. There is no forget, deletion, replacement or recovery-adoption method.

Synthetic verification covers preserved legacy bytes, multiple owners, restart retention, actual writer journal anchoring, missing cleanup, unknown cleanup, replay, conflicting anchors, malformed/truncated/partial files and injected write/fsync failures. Windows directory-entry power-loss durability remains unverified. Production composition remains unconstructed: it still needs a reviewed bridge from its pending-reference/current-owner callbacks into this companion inventory, a durable current-helper cleanup callback, failure/restart scheduler reservation admission, and proof that the entire scheduler path requires a fresh anchored ISO receipt before job success. No native runtime operation was performed for this unit.

## Durable current-helper bridge, still disconnected from scheduling

`createDurableIsoHostBuildAdapter` now binds the native host composition to the separate ISO recovery inventory. Its pending reference creates an exclusive durable job record before the first current-input helper. Every precise current-helper owner and cleanup outcome is appended separately under the same captured job/project/grant/runtime/journal binding. Cleanup evidence persistence remains possible after cancellation or grant revocation; persisting an observation does not restore authority. Current-input transport awaits its cleanup callback before admitting captured metadata and persists unknown cleanup before rejecting it. Failed cleanup persistence also prevents result admission.

Final reference progression preserves the transaction anchor, requires all current helpers to have matching verified absence observations and repeats actual anchored journal readback. Mocked full composition verifies this ordering with multiple current helpers, actual transaction/recovery files and restart inspection, and preserves incomplete evidence after unknown current-helper cleanup or producer failure. The operations service and scheduler still do not construct this adapter. Reviewed scheduler reservation/restart admission and the final job-success integration remain incomplete.

A dedicated regression injects failure in fsync of the final verified recovery record. The write API throws and does not report successful persistence. A later read may find complete bytes and a matching historical transaction anchor; that read still returns `grantsAuthority: false`. It establishes neither power-loss durability nor runtime absence, lock release, retry authority or successful completion of the failed write call. No poison or release mechanism is introduced to change that distinction.

Incomplete transactions retain in-memory locks. An exclusive store-wide `active.json` reservation also blocks all new transactions after restart, including transactions with a different job ID. This conservative serialization is intentional until scoped recovery is implemented. Only synchronized successful receipt completion removes that reservation. There is no unlock or reservation-adoption API. A crash during a record write may leave a partial record and remains incomplete. This store must use a private application-owned directory and must not be exposed to renderer-supplied paths.

Exclusive reservation creation synchronously notifies the coordinator before the first reservation write or fsync. Lock retention therefore does not depend on `begin()` returning its journal. Reservation write, reservation fsync, initial-record write and initial-record fsync failures retain all three memory locks and the durable reservation. Failures before exclusive acquisition release the caller's memory locks. Fault-injected regressions exercise all four post-acquisition boundaries; each produced a red result before the retention repair and passed afterward. Native runtime and power-loss recovery remain unverified.

Focused verification covers the transaction sequence, competing writer, forged/cross-job lease, retained interruption, unknown cleanup, cancellation before capture, stale output, changed grant/configuration and cross-job output replay. No WSL or container operation is part of this verification.
