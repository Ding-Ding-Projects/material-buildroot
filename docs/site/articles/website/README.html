Documentation website

This documentation website renders the current public planning documents and source wiki directly. Its visitor workbench keeps personal planning data in the browser; an optional companion panel can request only scoped read-only summaries from an explicitly paired desktop session. Production feature parity remains unchecked in the roadmap.

.\build.bat --target documentation /s

The root entrypoint acquires the pinned portable tools and the exact website/package-lock.json dependencies with lifecycle scripts disabled. It generates and validates an isolated output, then activates .cache/documentation-output/ with the standard source-bound build-receipt.json. Production never changes tracked documentation. The source, index and manifest must remain unchanged throughout the build.

After review and browser verification, promote generated index.html, .nojekyll, service-worker.js and site/ from that output into docs/, preserving the Markdown sources. The root service-worker.js is required for the visitor's explicit offline-document caching action. GitHub Pages continues publishing main → /docs; local generation, promotion, public deployment and live verification are separate checks.

The generator derives the checklist from ROADMAP.md; website visitors cannot change the authoritative completion state. Build metadata records the actual build time, base Git commit, whether inputs differ from that commit, and the SHA-256 of the exact input snapshot, including raw bytes of every locally referenced image and data asset. Decoded references reject Windows drive, backslash and control-character forms; source and output paths reject linked ancestors and root escapes. A clean commit containing generated output necessarily follows generation. Never describe the base commit as the entire built source when the snapshot differs.

The website uses genuine registered @material/web buttons, icon buttons, chips, text fields, selects, switches, lists, checkboxes and progress indicators, bundled locally with licensed Roboto font files. The component inventory maps each control to its actual primitive. Native authored form controls and generic disclosure substitutes fail validation. Semantic prose links and tables remain ordinary accessible content.

The site has local theme/heading-language preferences, document search and phase filtering. Search reports the complete match count while showing up to 12 results, supports arrow-key entry and Escape dismissal, and closes when focus or a pointer moves outside it. The mobile navigation drawer contains focus and returns focus when a viewport change hides navigation. The visitor workbench adds local goal/checklist/session-note persistence, reset, validated JSON import/export and explicit offline-document caching through a scoped service worker. Its companion panel accepts a manually pasted, short-lived challenge, checks a private IP HTTPS endpoint, and can read the workspace summary, saved project names and recent job states. It stores only the endpoint; challenge values, CSRF and session details remain transient. The website never presents raw host paths or job logs and does not infer that disconnecting canceled host work. Pairing still depends on the desktop-created exact-origin, read-only challenge, owner approval, normal browser TLS trust, CORS and private-network access. There is no QR claim or transport bypass. Visitor data does not grant desktop access by itself. It must fit phones from 320 CSS pixels, with reachable touch controls, a scrolling focus-managed navigation drawer and readable articles. These bounded controls do not complete the broader shared feature catalogue or complete article localization.

The home page is an interactive field guide rather than a Markdown directory: it teaches the source-to-image workflow, saves local walkthrough progress, previews a bounded generic-package recipe without network or file access, and guides visitors through documented troubleshooting decisions without probing the host. Visitors can bookmark canonical articles in the same browser profile and open the complete reference library for source text. A separate status page links to the GitHub latest-release page, describes implemented workspace surfaces and keeps unverified native Windows, WSL, Docker, guest and update behavior explicit. The visitor-workbench entry leads to a private browser plan, session notes and exportable backup. Roadmap work is divided into Planning & foundations, Buildroot workflows, Built-in tools, and Website/companion/release. Every category and each of the 11 phases has its own route. Phase pages show their own task checklist, prerequisites, evidence criteria, breadcrumb and previous/next navigation. Documentation recursively includes all Markdown below docs/ and design/, excluding generated docs/site/, with category indexes and individual article routes. Nested evidence and historical design records remain included. Referenced images and data assets are copied locally and checked byte-for-byte. Downloads/status is separate. The full source roadmap remains available as a reference record, not the primary all-tasks interface.

For actual browser verification, serve docs/ under /material-buildroot/, install the pinned Playwright browser or use an available Chromium through DOCS_CHROMIUM_PATH, then run node website/verify-browser.mjs. DOCS_TEST_URL selects the local test URL or the intended GitHub Pages URL. DOCS_OUTPUT_ROOT selects the exact generated output being served. The check compares served HTML, JavaScript and CSS with that output and retains genuine screenshots plus a source/artifact-bound receipt in ignored .cache/browser-evidence/; DOCS_EVIDENCE_DIR selects another evidence destination. Reviewed evidence can be promoted separately, so an exploratory run cannot change the source snapshot it is verifying. Browser proof remains separate from native Windows and public hosting proof.

The root documentation build validates generated internal routes and fragment destinations, document inventory, roadmap identity uniqueness, completion/evidence links and source metadata. Browser interaction and visual inspection are separate evidence. Rebuild after changing an included document so the website cannot retain an old checklist.

The GitHub wiki service has no accessible initialized repository at the time of initial authoring. docs/wiki/ contains the canonical starter wiki content and is rendered in this website. Synchronization with GitHub's separate wiki service remains pending.
