Scheduled preferences core and host service

香港粵語

src/shared/scheduled-settings.mjs is a portable offline scheduling candidate. It validates rules, evaluates civil-time windows, resolves temporary per-setting overrides, guards external-source results, and defines a persistence/history transaction seam. It performs no network access, native storage operation, setting mutation, timer polling, token lookup, or renderer action. Existing application build-job scheduling has a different purpose. The sibling browser preference schema is not adopted or claimed compatible.

Explicit admitted setting registry

Every operation requires a host-admitted registry mapping exact setting keys to synchronous validators. Keys are flat identities, never object paths to execute. Only registered settings with values accepted by their validator can appear in base values, rule values, or external results. The generic core does not ship a frozen hand-picked appearance list; consumers must admit their actual language, theme, density, color, typography, motion, display-name and other exposed appearance/customization consumers independently. Each validator must enforce its real consumer's complete value schema. Never admit credentials, authorization, file authority, private vocabulary, or broker effects as schedule settings. An asynchronous validator does not count as a successful validation.

The evaluator returns an isolated flat values object and provenance. It never assigns arbitrary nested properties, evaluates code, changes permanent base settings, or claims that a GUI actually applied the returned values. Actual application/reset, unavailable-value explanations, School mode precedence, localization, visible scheduling controls, search/palette routes and accessibility remain consumer integration work.

Version 1 rule document

The exact root fields are schemaVersion: 1, nonnegative integer revision, explicit timeZone, and ordered rules. Unknown versions have no silent migration. Revision is bounded below the largest JavaScript safe integer; the store rejects revision exhaustion instead of wrapping. Timezone must be understood by the installed Intl.DateTimeFormat implementation. Use an explicit IANA timezone or UTC; ICU aliases accepted by the runtime remain accepted rather than inventing a separate timezone table.

Each rule has exactly id, label, enabled, priority, startDate, endDate, startTime, endTime, days, values, and source. IDs are stable one-to-80-character ASCII identifiers, unique within the document. Labels contain one to 160 Unicode code points without C0/DEL controls. Enabled is Boolean; priority is an integer from -1000 to 1000. Dates are null or real Gregorian YYYY-MM-DD dates, years 0001–9999, with inclusive start/end bounds. Times are required HH:mm values from 00:00 through 23:59; a partial window is rejected. Days is exactly {type: 'everyday'} or {type: 'weekdays', weekdays: [...]} with one to seven unique numbers, Sunday 0 through Saturday 6. Every day is one rule, not seven copies. Values is a nonempty map of admitted setting values. Empty schedules are valid.

Limits are 262,144 original UTF-8 document bytes, 256 rules, eight nested container levels, 256 keys per object, 256 array items, 160 Unicode code points per object key, 4,096 per generic string, and 16,384 serialized UTF-8 bytes per setting-values map. Narrower field/source limits also apply. Scalars must be JSON-compatible and finite. Unsafe object keys, extra root/rule/source fields, duplicate decoded JSON keys, invalid UTF-8, malformed JSON, invalid calendar dates and unsupported settings are rejected as a whole. parseScheduleBytes(bytes, options) enforces original wire bytes and duplicate keys before returning a validated document; validateScheduleDocument(input, options) validates already parsed data and returns an isolated copy. Typed callers must not silently feed a duplicate-key JSON payload through ordinary JSON.parse first.

Civil-time and daylight-saving semantics

evaluateSchedule({document, base, at, registry, ...sourceOptions}) takes an explicit epoch-millisecond instant. It uses Intl.DateTimeFormat with the document timezone, Gregorian calendar, Latin digits and a 24-hour clock to find the actual local civil date and minute. No local UTC offset is invented. Start is inclusive, end exclusive.

A start earlier than end is an ordinary same-day window. A start later than end crosses midnight: the early-morning segment belongs to the previous civil start date for both date bounds and weekday selection. A Friday window ending Saturday at 02:00 still applies Saturday at 01:59 even if Friday was the final allowed start date. Saturday at 02:00 is outside it. Before the first allowed start date, an early-morning segment cannot borrow a future start date.

Equal start/end means the entire selected civil calendar day, midnight through the following midnight, regardless of the displayed equal time. It is not a 24-hour elapsed duration anchored at that time. Thus a daylight-saving spring day may have 23 actual hours and an autumn day 25. Nonexistent spring-forward minutes never match because no actual instant has that wall time. Repeated fall-back minutes match during both occurrences. Calendar-day subtraction for overnight anchoring uses a Gregorian date representation only, not timezone-offset arithmetic.

Among matching rules, greater priority wins; equal priority uses the later document-array position. Resolution occurs separately for each setting, so a high-priority rule that changes only theme cannot erase a lower-priority language override. When an override ends, each setting returns to another matching rule or its unchanged base value. No derived remote value is persisted into permanent base settings.

Sources and actual privileged boundaries

Source is one of these exact descriptors:

  • Local: {type: 'local'}. Apply the rule's admitted local values.
  • HTTPS: {type: 'https', url, refreshMs, timeoutMs, maxResponseBytes}. A validated response can supply any subset of the exact setting keys admitted by that rule's values map, never other settings.
  • Home Assistant: {type: 'home-assistant', baseUrl, entityId, refreshMs, timeoutMs, maxResponseBytes}. The base URL must be an origin root. Entity is a binary_sensor or input_boolean with a bounded lowercase identifier. Boolean on enables the rule's local values; off applies no values.

The host supplies an exact allowed-origin list. URLs must already have canonical spelling, an ASCII path, no duplicate slash segments, and no query, fragment or embedded credentials. Dot traversal and encoded path components are rejected rather than normalized into a different destination. HTTPS is required. HTTP is accepted only when the host separately enables loopback development transport and admits the exact localhost, 127.0.0.1, or [::1] origin and port. Refresh intervals are 30 seconds to 24 hours, timeout 100 milliseconds to 30 seconds, response limit one to 65,536 bytes. Tokens and vault references are not allowed descriptor fields.

These syntax checks do not resolve DNS or establish SSRF safety. The privileged provider described below independently enforces resolved destination/pinning policy, denies redirects and private/link-local/metadata destinations except explicitly enrolled Home Assistant or development destinations, bounds original response bytes and execution time, owns cancellation, and classifies offline/authentication/rate-limit failures. Home Assistant tokens come from its protected vault binding under a stable account key and never enter rules, responses, logs or ordinary history. The portable core itself makes no network requests.

External result generation and cancellation

createExternalScheduleCoordinator(options) coordinates actual future provider calls without making them:

  1. reset(document) validates the exact new configuration, increments generation, aborts existing requests, and revokes all old result receipts. Call on every document change, including same-revision external edits.
  2. reconcile(document, at) aborts requests and removes results for windows that have become inactive. Call when observing a new clock state before deciding whether to fetch. Re-entry can then request fresh activation data.
  3. begin(document, ruleId, at) admits an active external rule, checks exact document identity, enforces its minimum refresh interval, and returns a single request token with AbortSignal. Starting a permitted replacement request aborts the old one. The privileged provider uses only the admitted rule descriptor, never renderer-supplied network instructions.
  4. settleBytes(token, bytes, at) parses bounded original UTF-8 bytes, rejects duplicate keys and validates the response. settle(token, payload, at) is the already-strictly-parsed provider seam. Obsolete or consumed tokens, elapsed timeout, cancelled generations and invalid values cannot replace a newer result. An obsolete malformed response cannot abort a current request.
  5. snapshot() supplies immutable, ephemeral receipts for evaluateSchedule; cancel() aborts and revokes everything. A captured old snapshot is revoked by cancellation or result replacement. Receipts bind exact configuration identity and cannot be reconstructed by serialization or replayed against same-revision rule edits.

The exact response is {schemaVersion: 1, status, values}. Status is ready, off, or failed. HTTPS ready values must be a nonempty valid subset of rule keys; off/failed values must be empty. Home Assistant responses always have empty values: ready means verified on and uses the rule's local values. Off means verified off. The provider must map actual validated Home Assistant Boolean state into that result; missing token/unavailable/unknown states must never become ready.

Valid results expire after one admitted refresh interval from observation. Absent, expired, failed, invalid and off results fall through to another matching local rule or base per setting. Generic issue codes and rule IDs identify recovery context without preserving response bodies or tokens. The coordinator supplies generation guards, not an automatic background loop. The host still owns bounded activation/background refresh, clock-change observation and localized nonblocking recovery notifications.

Persistence and history seam

createScheduleStore({adapter, ...options}) serializes load() and replace(document, {expectedRevision}). It snapshots candidate data, reloads and validates committed bytes, checks revision, then asks the adapter to atomically compare the exact observed bytes and commit new bytes plus a history receipt. Missing storage uses expectedRevision null; the first committed revision is zero. Later replacements increment exactly once. The final document is revalidated after incrementing, so revision growth cannot publish an oversized record. Queue failure does not poison future operations.

The required adapter is read(): Promise<Uint8Array|null> and commit({expectedBytes, bytes, receipt}): Promise<boolean>. Commit must return true only when exact observed-byte comparison, document persistence and append-only history receipt are one committed operation. False means conflict; exceptions mean unavailable. Receipt includes only version, create/update action and from/to revision. The actual owner can bind it to its complete approved history model in that transaction. This seam does not itself provide a filesystem lock, atomic compare-and-exchange, browser transaction, durable history backend or independent-process ownership. An adapter that updates document and history separately does not satisfy it. No workspace store or host storage was changed in this unit.

Actual verification and remaining acceptance

node --test tests/scheduled-settings.test.mjs passes twelve focused tests on Linux. They exercise per-setting precedence/base restoration, everyday and selected weekdays, date boundaries, overnight end-date spillover, equal whole-day semantics, actual IANA timezone conversion, both repeated DST hours, skipped spring minutes and a 23-hour calendar day; strict limits/schema/source admission; stale/timeout/invalid/off results; Home Assistant Boolean behavior; duplicate raw responses; cancellation/revocation; exact configuration binding; and serialized transaction/history conflict/failure/reload behavior and exact revision-growth byte boundaries with an in-memory adapter.

The core module performs no network or native mutation. The host implementation and its separate verification follow below. Browser persistence, actual user-provider enrollment and native token vault acceptance, full registered setting consumers, schedule editor and history UI, localization/accessibility, supported-host clock changes, runtime screenshots, native Windows and independent A/D/C acceptance remain open. Passing offline core tests does not complete the scheduled-settings feature.

Private per-profile SQLite persistence candidate

src/main/preferences/schedule-store.mjs now supplies createSqliteScheduleAdapter({directory, profileId, registry, ...sourceOptions}). Directory and profile identity are trusted host configuration, never renderer paths. It implements the core adapter's real read and commit, plus history({after,limit}) and close. Two instances can observe the same database and resolve document conflicts through SQLite transactions and exact observed-byte comparison. Profile rows and history queries are independently scoped. Document replacement and append-only revision receipt insertion commit in one SQLite transaction; a failure rolls both back. History pages load at most 100 rows and never prune prior receipts.

The fixed database has its own application ID and version, exact STRICT table/index inventory, disabled extension loading and untrusted schema, DELETE rollback journaling and FULL synchronization. Pre-existing foreign/empty database files, unsupported headers/schema, links/hardlinks, replaced directory/database identities, WAL/shared-memory files, malformed ownership checkpoints and unknown rollback journals are preserved and refused. It does not mutate an existing settings or workspace store. The caller supplies admitted setting validators; source/token secrets do not belong in this database.

A sentinel-only write forces creation of SQLite's rollback journal before application document/history changes. The adapter atomically flushes a private checkpoint binding that journal's file identity to this database identity, then performs the actual rows. A known owned journal can therefore be admitted on restart and SQLite can roll back interrupted payload writes. A crash before that ownership checkpoint may leave an unproved journal; it remains preserved and unavailable rather than guessed safe. The checkpoint is protocol ownership evidence in a trusted private directory, not cryptographic protection against someone who can replace that directory's contents. No stale journal is blindly deleted and no foreign journal is submitted for recovery. SQLite handles admitted journal recovery itself.

node --test tests/schedule-preferences-store.test.mjs passes ten tests on Linux: real multi-instance compare/commit with profile-isolated paged history; rollback after both actual row writes; an actual separate writer killed by SIGKILL after the ownership checkpoint and uncommitted large document/history writes, followed by reopen, preserved old revision/history and successful next commit; foreign/header/sidecar/hardlink/corrupt-checkpoint preservation; bounded materialization of oversized database rows/history/checkpoints; and unexpected active-journal regular/symlink preservation with an unavailable profile latch. These tests use actual Node SQLite. They establish this exercised process-crash route, not Windows ACL/reparse semantics, universal power-loss durability or every interruption phase. A synchronous afterWrite fault hook exists for these tests and is not a renderer operation. No native profile integration or GUI acceptance is claimed by this adapter.

An unexpected journal replacement discovered during a live transaction is moved, without following links, to a unique retained name before SQLite rollback/close can clean the journal pathname. A retained incident records only relative retention identity, type, byte count and optional link-text digest. The original name is restored only by create-new hardlink semantics if absent; a newer replacement is never overwritten. The retained name and incident are not pruned. Both current and restarted adapters remain unavailable until explicit owner recovery, even if rollback restored prior data. Parent/file identity checks and bounded symlink inspection apply, but no absolute hostile-parent-race guarantee is claimed. Schema metadata, documents and history use bounded SQL projections; checkpoint reads use bounded retained descriptors with fatal UTF-8 and duplicate-key rejection.

Privileged external provider candidate

createScheduleSourceProvider in src/main/preferences/schedule-provider.mjs accepts a host-owned enrollment array. Each exact enrollment contains origin, kind, explicit private Home Assistant address list, development-loopback flag and optional protected credential reference. Rules cannot enroll destinations or credentials. The service initially supplies an empty array, so no external source is available by default. Origins, reference binding, private-address consent, optional trusted CA and resolver injection belong to trusted host setup; there is no new renderer token-entry or origin-enrollment API.

The provider resolves all DNS answers, rejects a mixed/unapproved answer set, pins one admitted numeric address into a new nonpooled connection, and verifies its connected remote address. Public API destinations cannot use private, loopback, link-local, metadata, multicast, unspecified, documentation or mapped-private addresses. Private Home Assistant access requires exact separately enrolled RFC1918/ULA addresses. Link-local/metadata targets stay refused even when listed. Loopback development requires both an explicit loopback origin and its separate development flag; plain HTTP is otherwise refused. IPv4-mapped IPv6 retains its actual transport family while sharing normalized address identity checks. TLS certificate validation remains enabled, including fixture requests; an explicit host CA can extend trust but no rejectUnauthorized=false bypass exists.

Only GET is used. Redirects are rejected, not followed. Raw response bytes, whole-operation time, active work and response encoding/type are bounded; status/authentication/rate-limit failures produce generic codes. Cancellation and timeout cover resolver, vault and socket phases. A timed-out unabortable resolver retains its concurrency slot until the underlying operation settles, preventing an accumulating hidden backlog. Every asynchronous phase rechecks cancellation before opening a socket or applying a result. Raw rule data is snapshotted through strict validation before asynchronous work. The core coordinator still owns version/schema/setting validation and generation acceptance; use settleBytes with provider results.

Home Assistant uses only the admitted /api/states/<boolean-entity> route. The protected token is read through the existing vault API with a stable origin-derived schedule_ha_ account owner. It is sent only as that enrolled request's Bearer header. Missing/refused token lookup fails explicitly, without silently ignoring credentials. Exact requested entity identity and verified on/off state are checked, then mapped to the core's empty-value ready/off envelope. Neither token nor upstream body is returned, logged or persisted by this provider. No real user's Home Assistant or native credential store was accessed.

node --test tests/schedule-provider.test.mjs passes seven tests using actual task-owned local HTTPS with a locally trusted certificate: composition into the core; redirect/body/auth/rate/certificate failures; fixture on/off and stable protected reference lookup; private/mapped/link-local/mixed DNS refusal; timeout/concurrency/cancellation; actual socket cancellation; and mapped IPv6 transport. These are provider-fixture receipts, not live enrolled-provider or native-vault proof.

Host preference service and current consumer boundary

createSchedulePreferencesService in src/main/preferences/service.mjs composes storage, coordinator and provider with the actual current admitted keys only: language and appearance.theme. Their choices match the present application consumers. The reusable core can admit future real setting consumers, but this host service does not claim the full appearance catalogue is implemented.

The host supplies directory, profileId and baseReader. It can also supply trusted enrollment/vault/provider dependencies. The base reader must return both actual persisted values or throw; no fake default replaces a failed setting read. start owns a real directory watcher and bounded clock tick. Local persistence changes are reloaded, evaluated at the host clock, and published through subscribe/status. read returns the local validated document or null; replace persists it; history pages real local receipts; refresh performs admitted active external work; cancel aborts/revokes current results and pauses external refresh for at least 30 seconds; close releases watcher/timers and cancels providers. evaluate({at}) is a host-only preview and never publishes an arbitrary preview clock into live events.

The exact safe event snapshot is available, watching, running, revision, externalAvailable, effective and evaluatedAt. Effective contains only the two admitted values, per-key provenance, applied rule IDs and generic issue codes. It contains no document, URLs, response bodies, references or tokens. Unreadable storage/base or unavailable watching produces unavailable with effective null, not invented base state. Empty enrollments report externalAvailable false. That flag indicates enrolled capability, not current provider health; actual failures remain per-rule generic issues.

replace accepts an optional trusted per-invocation authorize callback supplied by the IPC owner, never from renderer JSON. It checks before work, after awaited reads and immediately before the actual synchronous SQLite commit boundary. A frame revoked while a read is pending cannot cause document/history mutation. Authorization cannot retroactively undo an already committed transaction; a closing consumer must reread actual state rather than infer rollback from an undelivered reply. No global mutable authorizer is shared between requests.

node --test tests/schedule-preferences-service.test.mjs passes five tests for real SQLite/watch/evaluation and preview isolation, exact event fields, unavailable watch/storage handling, lifecycle closure, and revoked-frame pending-read refusal with zero actual document/history effects. No renderer scheduling editor, native enrollment/token setup, full appearance consumer matrix or Windows/runtime acceptance is claimed here.

The service refresh queue uses two bounded workers, creating each coordinator request only when its worker dispatches it. Later rules therefore receive attempts without starting their timeout while waiting behind earlier rules. Effective issues are deduplicated by rule identity, with a precise provider diagnosis taking precedence over a generic core fallback; the issue list cannot double the rule bound. The service regression uses five actual TLS-backed rules, proves all receive an attempt with at most two concurrent requests, and proves five authentication failures produce five unique issues while lower-priority local values remain effective.

Additional store failure checks prove that an already-existing foreign incident record cannot bypass SQLite close or retain a live writer lock. Incident publication failure after retention preserves the foreign incident and still closes the database. A failed retention rename uses create-new hardlink retention with verified identity before removing the old name. Retained names remain available for explicit recovery, and subsequent profile reads are unavailable. Simultaneous inability to perform all retention writes or hostile parent replacement is not an absolute recoverability guarantee; no such guarantee is claimed for physical storage failure.

Desktop bridge

The main process creates the service in its private application profile and reads base language and theme from the existing persisted settings and workspace stores. External enrollment starts empty. Startup failures expose unavailable status; shutdown cancels the service and waits with the owned operations before exiting.

The sandboxed bridge accepts status, read, replace, history, refresh, cancel and the three explicit enrollment actions described below. It rejects unknown or duplicate fields, oversized UTF-8 requests, renderer clocks, host paths, transport overrides and protected credential references. The admitted frame is checked before work and after awaited results; every mutation receives a live authorizer checked again at its commit boundary. Unsubscribing removes only the caller's listener. Events are strictly filtered and frozen, and contain neither source descriptors nor credentials. Request failures expose allowlisted generic codes.

The combined scheduling run passes 40 checks across core, store, provider, service, IPC and the existing desktop preload contract. The IPC integration uses the actual SQLite service to save, refresh, read, detect conflicts and retrieve history while confirming base values remain unchanged. It is Linux source verification, not packaged Windows or GUI acceptance.

Explicit persisted source enrollment management

The host preference service now exposes enrollmentList(), enrollmentSave(input) and enrollmentRemove(input), backed by src/main/preferences/source-enrollments.mjs. The sandboxed bridge admits these through exact enrollment.list, enrollment.save and enrollment.remove requests. Graphical enrollment and native user-credential acceptance remain separate work. List/save/remove return {available: true, revision, entries} only on successful reads. Each explicit settings-list entry contains a stable opaque ID, user label, exact origin, source kind, exact private address choices and credentialConfigured. The Boolean means a protected reference is stored, not that the native vault or token has been tested successfully. Protected references and tokens never appear in these replies or live events.

The private profile file has exact format/version/revision/entries fields. It permits at most 32 entries, one per exact origin, with generated UUID identities, labels up to 96 Unicode code points, HTTPS origins up to 2,048 characters and at most 16 private addresses per Home Assistant entry. The complete file is bounded to 128 KiB. Origin spelling must be canonical and contain no path, query, fragment or embedded credentials. Plain HTTP and loopback development enrollment cannot be supplied by these user operations. Development flags, CA material, custom resolvers, file paths and caller-supplied vault references are rejected. Existing trusted fixture-only provider configuration remains a separate host dependency.

Private address choices require explicit Boolean consent and exact RFC1918 IPv4 or ULA IPv6 literals; they cannot introduce metadata, link-local, loopback or broad CIDR authority. Provider DNS/IP and connected-address checks remain unchanged. Setup performs no DNS resolution, socket connection, fetch or token-read request. A Home Assistant token is accepted only as transient enrollment operation input, then written through the existing protected vault under its stable origin-derived account owner. It is not recorded, returned, logged or added to ordinary schedule history. Every rotation writes a fresh protected reference before atomically publishing metadata; prior references are never overwritten or automatically pruned. Retaining an existing credential requires explicit retainCredential: true with the same origin/kind and no new token. Omission alone never means retain or clear.

Save/remove require the observed enrollment revision. They serialize cross-instance mutation through a create-new token-owned lock and compare exact observed file bytes/identity again after asynchronous vault work and immediately before publication. The operation-specific trusted authorizer is checked before work, after vault awaits and before mutation. Revoked or failed enrollment cannot publish a new record; a safely orphaned new vault reference is retained if publication fails or outcome is unknown. Files use bounded no-follow retained-descriptor reads, decoded duplicate-key rejection, exclusive temporary writes, file flush and atomic rename; parent directory flush is performed on Linux. Foreign, corrupt, oversized, linked and replaced storage is preserved and unavailable. A crashed writer's unproved lock is not automatically removed. These cooperative ownership checks do not claim an atomic filesystem compare-and-exchange or universal power-loss/native ACL proof.

Stored schedule syntax and network authority are now deliberately separate. schedule-validation.mjs derives origins only to validate bounded local rule data; it cannot grant a socket. Old or newly stored unenrolled origins remain inert, allowing local rules, editing and base fallback to remain usable after enrollment removal. The provider continues to admit only the actual current enrollment map. Missing enrollment reports SOURCE_NOT_ENROLLED; unreadable enrollment storage reports SOURCE_ENROLLMENTS_UNAVAILABLE. It never makes a malformed enrollment file invalidate the whole local schedule profile or silently turn a URL into network permission.

The service observes enrollment file changes, replaces the provider map, aborts the old provider, revokes prior generation receipts and recalculates temporary values without modifying saved rules or permanent base values. Failed enrollment reads/publication trigger the same authority refresh/revocation path. Live status stays payload-free; source details are available only through the explicit settings-list operation. Empty/unavailable enrollments do not claim an external source is ready.

node --test tests/schedule-source-enrollments.test.mjs passes thirteen focused tests. These cover restart/list/replace/remove, independent-instance conflicts, private consent/address restrictions, rejected unreviewed fields, exact inventory bounds without pruning, protected fresh-reference rotation and explicit retain, frame revocation or service closure during a pending vault write with no published metadata and no abandoned owned lock, retained orphaned references, corrupt/foreign/duplicate/oversized/link preservation, same-revision concurrent edits, failed publication preserving prior metadata, inert removed-source rules and local fallback, and an actual TLS fixture proving active generation revocation and no additional setup socket/DNS work. Independent review found and repaired a replacement-options mismatch: changing or removing a persisted external origin now preserves strict validation, advances the actual SQLite revision and grants no network authority. The vault is a controlled test implementation; no real user Home Assistant or native vault proof is claimed. GUI enrollment, production credential prompts, independent A/D/C controls and Windows acceptance remain open.

The current host/enrollment/IPC/preload run passes 43 checks. It includes actual enrollment save/list/removal through the desktop boundary, protected-reference-only persistence, no secret in replies, no setup DNS and revoked-frame mutation refusal. This result is separate from the earlier 40-check core/host run and the previous full Node suite.
