Native file capabilities

香港粵語

Native dialogs establish session-only file authority. Renderer-supplied paths never establish grants. Project grants are owner-bound random identifiers, expire after five minutes and carry read or read/write access. Trusted host import adapters can issue read-only single-file grants with importFile; this method is not exposed to the renderer. Existing project folder selection and tool input/output dialogs remain the native acquisition routes.

Every grant acquisition and resolution inspects the volume root and each existing component, records device/inode/birth identity and compares the exact native real path. Symbolic links, junctions that resolve elsewhere, hardlinked files, special files, case aliases, network/device paths and Windows reserved names or trailing-dot/space aliases are rejected. Replacing a parent or selected object invalidates the grant. A changed project grant is revoked. New outputs require an existing inspected parent and cannot overwrite an existing file.

The main-only translate adapter resolves its grant before calling a trusted host converter and resolves and compares the inspected object again afterwards. It accepts only a normalized absolute POSIX result, without control characters, backslashes or double-leading slashes. The converter is a host function, never renderer code or a command string. Existing execution adapters continue to own their WSL and container path mappings; this adapter does not admit an additional runtime or shell command.

Limits and deferred verification

Path inspection is not an operating-system handle-relative sandbox. A concurrent external process can still race a later path-based open after resolution. Consumers must resolve immediately before use, use exclusive creation for outputs and retain existing execution admission rules. Unrecognized reparse mechanisms that preserve both the native path and object identity need native handle-based inspection before any stronger claim is possible.

This implementation was prepared under the requested speed mode. Tests, static analysis, independent review, runtime interaction and screenshots were deliberately deferred. PH02-T03 acceptance remains unverified, including native Windows reparse/case behavior and asynchronous translation cases.

Native broker source and packaging contract

The Win32 broker source is native/file-broker/main.cpp. Root build integration calls scripts/build/native-file-broker.ps1 -OutputDirectory <owned build directory> inside an initialized MSVC x64 developer environment with the Windows SDK. The helper emits material-file-broker.exe and a hash-bound broker-manifest.json; its runtimeVerified field is always false. No compiler bootstrap has been added. An unavailable compiler is a real build limitation, never permission to substitute a plain child process.

The host module src/main/security/native-file-broker.cjs accepts only host-owned payload manifests and a native grant resolver. It stages the hash-verified broker and explicitly inventoried decoder resources. Decoder arguments come from a compiled operation allowlist. Implemented pipe operations are ImageMagick PNG/JPEG/WebP and FFmpeg WAV/MP3/FLAC/MP4/WebM. Document conversion and archive reinterpretation/extraction remain outside this broker's implemented operation set; fixed ZIP packaging is described below. The seekable PDF subset is documented below.

The broker holds every ancestor directory without delete sharing, opens the input without write/delete sharing and checks its originally granted volume serial/file index using native handle information. It opens a private incomplete output beside the selected destination with exclusive CREATE_NEW semantics, rejects reparse tags, hardlinks and exact-path case differences, and retains data and parent handles for the complete operation. It publishes the validated file using a no-replace handle rename relative to the held destination parent. Failed or cancelled output stays under its explicit incomplete name; it is never promoted or removed through a later path lookup. Main-process grants expose their stored integer identity without rounding through floating-point file indices.

The decoder runs in a newly created zero-capability AppContainer with the all-application-packages access opt-out. Only its staged code/resources receive explicit AppContainer read/execute ACLs. The selected input and output paths receive no AppContainer ACL grants. An explicit handle inheritance list passes only input, output and a null diagnostic sink. No shell, inherited user environment or diagnostic content is exposed. The Job Object permits one process at a time, bounds memory to 256 MiB and total job CPU user time to 20 seconds. Conversion and decoder validation share one 30-second wall deadline. Output growth is polled every 20 ms against 128 MiB, so this is a termination threshold rather than a hard filesystem quota. Cancellation bytes or closure of the parent's control pipe terminate the owned job; broker process exit closes its kill-on-close job handle. Parent-side termination remains bounded.

The AppContainer profile is temporary and removed after process termination. Its operating-system-managed profile/registry behavior and platform resource access have not been exercised. The broker module's WeakSet identity establishes only that an object was produced by the trusted host factory. Neither this identity, a matching binary hash, a successful compilation nor the source mechanism establishes runtime isolation acceptance. Callers must retain unavailable/unverified external-adapter presentation until separately authorized runtime evidence exists.

No root build, native compilation, decoder execution, tests, static analysis, review or screenshots were run for this source contribution. Build-driver/resource integration is coordinated separately with the packaging owner. Actual packaging, native compiler availability, AppContainer creation, executable/DLL access under the low-privilege token, cancellation, every denial boundary and converter behavior remain unverified.

Validated-output receipt and failure preservation

A completed operation requires both a format signature and a second constrained decoder pass over the same retained output handle. Image validation decodes the requested PNG/JPEG/WebP format to the null sink under memory/dimension/frame-list bounds. Audio validation decodes WAV/MP3/FLAC to the null sink with fatal decode-error handling. The decoder receives only reduced-rights duplicates: read-only input and write-only output. The second pass cannot modify its input handle. Source and output SHA-256 values are calculated through retained handles using BCrypt. This validates bounded decode success, not preservation of every source sample, frame, pixel or metadata field.

Before either process is resumed, the broker queries its actual AppContainer identity, low-privilege status, exact profile SID, zero capability count and assigned Job Object. Unsupported LPAC token-query behavior fails closed; platform support for that query remains unverified. API setup alone does not produce a completed operation receipt.

The completed protocol contains the exact operation, source and output hashes, output byte count, signature-and-decoder-roundtrip validation, actual token/job admission fields and atomic-no-replace publication. The host accepts only that strict receipt. Its describe method verifies broker and decoder-package hashes and reports attemptAvailable with runtimeAcceptance: unverified; it performs no OS admission and is never a conversion or isolation acceptance claim.

On failure or cancellation after temporary creation, the broker retains .material-incomplete-<UUID>.tmp beside the selected destination and returns only its opaque basename plus a not-published state. If the broker is disconnected or forcibly terminated before its receipt arrives, the host reports unknown partial-output/publication state. It neither invents a successful rollback nor deletes a path that another process might have replaced. A caller must show that incomplete state truthfully and keep existing user files intact.

Microsoft documents handle-relative no-replace rename behavior in FILE_RENAME_INFO and LPAC identity in TOKEN_INFORMATION_CLASS. The implemented native calls and compiled API availability still require the deferred real-platform acceptance.

Bounded video operations and remaining adapter boundary

The compiled operation allowlist also has ffmpeg-mp4 and ffmpeg-webm. MP4 uses H.264 video with the veryfast encoder preset, YUV 4:2:0 pixels, optional first-stream AAC audio and fragmented MP4 output (frag_keyframe, empty_moov, default_base_moof) suitable for the inherited output handle. WebM uses VP9 with a fixed realtime encoding policy and optional first-stream Opus audio. Each operation requires the first video stream, maps only the first optional audio stream and drops subtitle/data streams, source global/stream metadata mappings and chapters. These are lossy fixed-profile conversions, not metadata-preserving or bit-exact transformations. Source dimensions/frame rate are not deliberately resized or truncated. Decoder, encoder, CPU, memory and output limits can reject an input rather than silently shortening it.

The MP4/WebM signature and second full-decoder pass use the same held output handle, strict receipt and no-replace publication as image/audio operations. Validation explicitly selects the expected audio/video demuxer and requires the intended media stream. The existing overall input/output/time limits are unchanged. The packaged FFmpeg profile must actually contain the requested encoders; package inventory alone does not establish codec readiness. Inputs that require seeking cannot assume that the inherited pipe:0 input protocol provides it, and may be rejected. The FFmpeg muxer documentation describes fragmented MOV/MP4 output options.

Generic document and archive operations, and PDF operations outside the explicitly implemented seekable subset below, remain unavailable. Pandoc/LibreOffice operations can need seekable named resources and controlled side files; GNU tar from the declared portable payload is not a ZIP stream writer; the current qpdf workflow requires seekable named/multiple inputs and operation-specific page/metadata readback. Supporting them requires a separate bounded host protocol with individually held resources, checked native publication and operation-specific validation. Neither package presence nor a global isolation flag admits those tools. No fallback to a plain host child process is supplied.

An invalid completed receipt also carries incompleteOutput: { state: unknown, publication: unconfirmed }, because the broker may have published before its reply was lost or damaged. The host must not infer that a missing or malformed success receipt means no output exists. These additional video operations and receipt changes have not been compiled or exercised by this source lane.

Seekable PDF page extraction and reordering

The native operation protocol now includes qpdf-extract and qpdf-reorder. The host accepts one read-only source grant, one exclusive new-output grant and an integer pages array with 1 to 1,000 entries, each between 1 and 10,000. Duplicate page numbers and caller ordering are passed as numeric selection data. No arbitrary qpdf option, path, argument file, password or shell command is accepted. Additional typed merge, rotation and metadata operations are described below.

The broker copies the held source into a newly created private data directory beside its staged runtime. Only three fixed names are used: source.pdf, validation.pdf and page-count.bin. Each PDF copy is bounded to 128 MiB, with the original input still limited to 64 MiB; the count stream is bounded to 32 bytes. No untrusted member name is used, no archive is extracted and no decoder-supplied side file is admitted. The AppContainer receives read/execute access to the data directory and read-only PDF copies. The count file is accessed only through the inherited write-only stdout duplicate.

Each copied PDF is hash-compared against its retained original handle. After the copying writer closes, the broker reopens a read-only handle, checks the same native file identity and exact path, compares its hash again, and holds that handle without write/delete sharing while qpdf uses the seekable named copy. The original selected paths never receive AppContainer ACL grants. The selected output remains a private held incomplete file until publication.

The operation first requires a PDF signature, successful qpdf --check, and a bounded --show-npages result for the input. Requested page numbers must fit that actual input count. It then invokes only the fixed page-selection workflow with output to the inherited stdout handle. The held output is copied to validation.pdf, checked structurally, counted, and compared by hash to the actual held output. Publication requires exactly the requested number of output pages and the existing no-replace handle rename. All qpdf processes share the existing single-process, total CPU, wall-time, memory and no-network admission limits. Warnings/nonzero qpdf exits fail closed.

PDF completion receipts contain the original ten admission/hash/publication fields plus inputPages, expectedPages and outputPages; validation is qpdf-structure-and-page-count. The host requires the exact thirteen fields and compares the expected count with the original request. This proves only qpdf structural success and the bounded page count. It does not independently prove visual equivalence, exact page order, accessibility-tag preservation or removal of active PDF content. It is not a sanitizer.

The qpdf 12.4.2 invocation documentation requires seekable input, permits non-seekable standard output, and documents both structural-check limitations and page-count output. This route supplies the missing seekable input through bounded read-only copies rather than broadening host file access. These new PDF source paths have not been compiled or exercised in this lane. Existing failure receipts still retain incomplete outputs or report unknown publication state; no plain-process fallback was added.

Multiple-input PDF merge and semantic readback

The additional typed operations are qpdf-merge, qpdf-rotate and qpdf-metadata. Merge accepts up to eight original read grants with aggregate original bytes at most 64 MiB, aggregate pages at most 10,000 and a bounded native argument budget. Every original is held, checked against its grant identity, hashed and copied to a fixed numbered source-N.pdf read-only staging resource. The order of those resources is the requested merge order. No renderer filename, qpdf option or argument-file path becomes a member name. --empty --pages merges all pages from each staged source in that order. This can lose document-level information such as outlines or other non-page data; it is not a preservation or sanitization guarantee.

Rotation accepts one source, a unique selection of at most 1,000 pages and a relative angle of 90, 180 or 270 degrees. The broker captures bounded qpdf JSON version 2 reports before and after processing. Its data-only reader resolves page references, inherited /Rotate entries and parent dictionaries with cycle/depth bounds. Every resulting page angle must equal the original angle plus the requested offset for selected pages, and remain unchanged for unselected pages. The page count must remain unchanged. This validates the effective page-rotation property, not a rendered visual comparison.

Metadata removal accepts only mode: remove. qpdf documents that --remove-info retains /ModDate, so the broker does not pretend that flag removes the entire information dictionary. Instead it generates a bounded read-only metadata-update.json containing the original trailer without /Info, applies the supported --update-from-json route and --remove-metadata, then reads back the result. Publication requires absence of trailer /Info and catalog /Metadata, with unchanged page count. This covers those two document-level fields only. Page-level metadata, content, embedded files, active actions, identifying image content and other document data are not claimed removed.

The reader in native/file-broker/qpdf-json.hpp accepts only bounded JSON data: at most 1 MiB per report, 20,000 values and 64 nesting/reference steps. Duplicate keys, malformed strings/numbers, unsupported report shapes and unexpected references fail closed. Report and metadata-patch resources use fixed names; no report data becomes a command. At most eight numbered input resources, one output-validation PDF, one bounded inspection report, one optional bounded metadata patch and one counter/scratch resource are created. The PDF copies remain within the existing byte limits; report/patch/scratch data is at most 1 MiB each, with qpdf page-count output itself still limited to 32 bytes. These limits may reject otherwise valid large or complex files. Every child shares the existing one-process, no-network, CPU/memory/wall-time limits.

Merge receipts have fifteen native fields: the existing thirteen PDF fields plus sourceSha256s and inputPageCounts, in the exact source-grant order. inputPages, expectedPages and outputPages must equal the sum of the input counts. Rotation receipts add degrees and rotationVerified, with qpdf-structure-page-count-and-rotation validation. Metadata receipts add metadataMode and metadataAbsent, with qpdf-structure-page-count-and-metadata validation. Rotation and metadata counts must equal their original input count. The host requires those exact field inventories and operation-specific values before returning completion. The existing two host fields remain separate.

The native source uses the official qpdf JSON version 2 representation and documented processing options. None of these additional routes has been compiled, exercised or visually verified in this lane. The protocol still has no generic document/archive execution, PDF inspection-only result, password intake or broad host-process fallback. Failure and unknown-publication preservation remain unchanged.

Isolated single-member ZIP packaging

zipstore-zip creates a new uncompressed ZIP containing the exact selected file bytes under one fixed safe member name, input.bin. This is explicitly file packaging, not conversion or extraction of an existing archive. Selecting an existing archive stores that entire archive as the member bytes. Original names, host paths, timestamps, permissions and comments are not copied; the archive uses a fixed DOS timestamp. The user-facing workflow must disclose those choices.

The worker is compiled into the same hash-verified broker executable and staged as its own exact payload. It runs as a separate LPAC child in the existing bounded Job Object. Its entrypoint itself requires AppContainer/LPAC status, zero capabilities and Job Object membership before reading any data handle. It receives only read-only input and write-only output handles. There is no host-process fallback, external archive command, filesystem extraction or writable decoder directory.

The writer in native/file-broker/zip-store.hpp accepts at most 64 MiB and emits exactly one stored ZIP member, bounded local/central/end records, a safe constant name and CRC32. A second isolated worker checks the exact record layout, member name/count, lengths, CRC32 and that the member SHA-256 matches the original held source digest. It rejects extra members, comments, paths, attributes, compressed methods and trailing bytes. The resulting archive is at most the input length plus 116 bytes. The existing held output hash, cancellation, partial preservation and atomic no-replace publication still apply.

The strict ZIP native receipt has twelve fields: the original ten admission/hash/publication fields plus memberCount: 1 and memberName: input.bin; validation is zip-stored-member-crc-and-source-hash. Its factory description reports only package-based attempt readiness with runtime acceptance unverified. No separate GNU tar or other archive payload is used for this operation. The writer/validator source and native worker route have not been compiled or executed in this lane.

Explicit strict-Markdown document conversion

The typed pandoc-html, pandoc-docx and pandoc-epub operations accept only sourceFormat: markdown-strict, not automatic document detection. Native input validation requires well-formed UTF-8 without NUL or unsupported ASCII controls. The fixed Pandoc invocation disables raw HTML parsing and uses --sandbox --fail-if-warnings; no filters, defaults files, user templates, PDF engines or renderer-provided options are accepted. The output is standalone with fixed title Converted and undetermined language und. Formatting and metadata can be lost; this is not a preservation workflow. External/embedded-resource needs that cannot run inside these limits fail rather than broadening file or network authority.

HTML output requires the expected standalone signature and a second sandboxed Pandoc HTML-to-JSON reader pass to the null sink. Raw HTML being disabled does not sanitize URLs or attributes. Generated HTML remains untrusted data: the application must never auto-render or execute it as trusted application content. This route performs no HTML sanitization and makes no safe-to-execute claim.

DOCX/EPUB output additionally passes the native structural reader in native/file-broker/zip-directory.hpp. It accepts only bounded simple ZIP layouts: at most 4,096 members, 512 ASCII bytes per member name, 32 path segments, 128 MiB per member and 256 MiB declared aggregate uncompressed bytes. It rejects traversal/absolute/device names, alternate streams, case duplicates, file/directory conflicts, symlink/special modes, unsupported methods/versions, encryption, ZIP64, extra fields/comments, overlapping members and unreferenced layout gaps. Local and central names/record facts must agree. DOCX requires core package members and rejects VBA/ActiveX member names; EPUB requires its stored first mimetype member, container and package manifest. Those checks are structural admission, not general macro/active-content sanitization.

A hash-matched read-only copy of the held document is then passed as explicit seekable input to the matching sandboxed Pandoc reader, which must successfully produce its internal JSON representation to the null sink. The native directory reader does not inflate or CRC-check every compressed member. Successful reader acceptance does not prove visual equality, correct pagination, accessibility or complete semantics. Strict layout/member/resource limits can reject otherwise valid generated packages. All children still use actual LPAC/token/job admission and the existing CPU/memory/time limits; failure/unknown output preservation and final no-replace handle publication remain unchanged.

HTML receipts have twelve native fields: the original ten plus sourceFormat: markdown-strict and readerAccepted: true, with pandoc-html-reader validation. DOCX/EPUB receipts have thirteen, adding bounded memberCount, with pandoc-reader-and-safe-zip-directory validation. These fields report only the successful operation-specific checks; factory descriptions still say runtime acceptance is unverified. The existing bundled Pandoc package and exact manifest inventory are required.

The source follows the Pandoc manual, including its explicit warning that generated HTML is not necessarily safe, and the ZIP format specification. These new document paths and the native structural reader have not been compiled or exercised in this lane. Generic input-document conversion, office-backed PDF production, archive extraction/reinterpretation and PDF inspection-only workflows remain explicit source gaps, with no plain-process fallback.
