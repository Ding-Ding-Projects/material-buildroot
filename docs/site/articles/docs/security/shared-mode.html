Shared experience mode host protocol candidate

香港粵語

src/main/privacy/shared-mode-service.cjs implements an explicit shared local host record, live observation, exact display rename, and locally verified exit. This is a reusable protocol candidate. No existing universal filesystem path or cross-application credential interchange was discovered in the canonical requirements. The caller must supply one admitted absolute sharedDirectory and a compatible shared protected vault to every participating application. A per-application Electron userData directory or browser-origin local storage cannot establish universal state.

Existing sibling browser preference code uses its own origin-local storage and broadcast channel. This candidate neither overwrites that format nor claims compatibility with it. Shared filenames alone also do not prove cross-product vault decryption; protected storage providers must use compatible account/provider identity, and actual supported-host interoperability remains unverified.

Exact on-disk protocol

The fixed record filename is shared-mode-v1.json, inside the explicitly supplied shared directory. The exact root fields are protocol, schemaVersion, revision, active, displayName, and credential. Protocol is the literal shared-experience-mode; schemaVersion is 1; revision is a fresh lowercase UUID version 4. Active is a Boolean. Display name is one to 96 Unicode code points, contains non-whitespace text, and excludes C0 controls and DEL. Its exact spelling and spacing are preserved.

Credential is either null or an exact object with kind and reference. Kind is pin, password, or passkey; reference follows the protected vault's vault: UUID format. An active record must have a credential. The complete file is bounded to 8,192 UTF-8 bytes. Unknown fields, versions, duplicate decoded object keys, invalid UTF-8, corrupt JSON, malformed credentials and foreign protocol records are rejected without initialization or overwrite. No password, PIN, hash, passkey registration, vocabulary bytes, imported-file metadata, or ordinary application preferences are stored in this record.

The stable vault owner is shared_experience_mode_v1. The host injects the existing vault-shaped API write(owner, protectedString) and read(reference, owner). Password and PIN verifier envelopes are stored as protected strings, with independent random 16-byte salt and 32-byte scrypt result. Derivation is asynchronous with fixed N=16384, r=8, p=1 and a 32 MiB memory bound; valid verifier comparison uses timingSafeEqual. PINs require four to twelve decimal digits. Passwords require eight to 1,024 Unicode code points; either input is at most 4,096 UTF-8 bytes. Secret confirmation is required during enrollment. Existing verifier material is not exported or returned.

Host API

createSharedModeService({ sharedDirectory, vault, passkey?, watchFactory?, watchRetries?, retryDelayMs? }) returns a service with declarations in shared-mode-service.d.cts:

  • start() admits the directory, starts observation, and loads current state. It never implicitly initializes or overwrites a record.
  • initialize({ displayName? }) creates an inactive record with no credential only when the record is genuinely absent. The shipped name is used only for explicit initialization without a chosen name.
  • enrollCredential({ expectedRevision, kind, secret?, confirmation?, current?, registration? }) installs a new protected verifier. If a credential already exists, current: {secret} or current: {assertion} must verify it before replacement. Failed verification or vault/persistence errors leave the old record usable. Orphaned new vault entries after a failed record commit are retained, not automatically pruned.
  • enter({ expectedRevision }) requires configured credential metadata and sets the mode active. It does not read or prove the stored verifier before entry; vault availability is checked during enrollment, replacement and exit. Consumers must not describe entry as a successful vault-health or future-exit guarantee. Unavailable exit verification remains an explicit error, with the user-managed reset route still available.
  • leave({ expectedRevision, secret?, assertion? }) verifies the current shared credential before setting inactive.
  • rename({ expectedRevision, displayName }) writes the exact chosen name. All consumers must use that chosen name everywhere, including accessible names and discovery text.
  • status() and subscribe(listener) expose only a safe current snapshot. reload() explicitly revalidates storage. close() cancels observation and stops new mutations.
  • recovery() returns the exact shared directory/record location and the experience-policy disclosure. There is no deletion or blind credential-reset method.

A snapshot contains available, watching, configured, active, displayName, revision, and credentialKind. It contains no protected reference or verifier. When state cannot be read or watched, availability is false and current configured/active/revision/kind fields are null. The last successfully observed exact chosen name is retained rather than replacing it with the shipped name. A healthy genuinely absent file is an explicit reset/unconfigured state; it is distinct from corrupt or unreadable storage. Deleting the shared record is the documented user-managed reset route and affects all participating applications.

A supplied passkey adapter must implement real enroll(registration) and verify(storedRegistration, assertion) and own challenge freshness, replay prevention, account binding, platform consent and cryptographic verification. Registration is protected in the vault. Without the adapter, passkey operations report PASSKEY_UNAVAILABLE; no fallback factor is invented. This code does not implement or prove a native passkey provider.

Concurrency, observation and storage admission

Every mutation obtains an exclusive shared-mode-v1.json.lock using create-new semantics, retains its random ownership token and file identity, reloads the actual record, checks the expected revision, and retains the exact admitted bytes and file identity. It rechecks those bytes, identity and lock ownership after asynchronous credential work and again immediately before publishing by atomic file replacement. Even an external edit that reuses the same revision, or replaces the inode with identical bytes, is rejected as stale and preserved. Another process receives a bounded busy error, not an unbounded wait or a silent stale write. If lock initialization fails after exclusive creation, cleanup removes only the proved original inode containing the exact full or partial prefix of its generated token; an unrelated replacement remains untouched. Only the exact owned lock identity and token are removed; an unowned, replaced, malformed, or stale lock is never automatically deleted. A crashed writer can leave its lock file behind and require explicit owner recovery. The service does not guess PID ownership, kill processes, or infer that a lock is stale from its age.

Writes use same-directory exclusive temporary files, file flush, and atomic rename. Failed record writes leave the prior committed file intact. Existing parent directory identities are retained and rechecked. Symbolic-link ancestors/files, hardlinked state files, replaced directories and unsafe file identities are rejected. Reads use no-follow descriptors where supported, validate identities before/after bounded reads, and do not load arbitrary file lengths. The final read followed by rename is not an atomic compare-and-exchange primitive. Cooperative writers must use this protocol lock. An uncooperative external writer can still race the final check and rename; these checks do not claim protection against all hostile concurrent filesystem races. Directory fsync/power-loss semantics and Windows reparse-point/ACL behavior require supported-host verification.

Directory watching survives atomic record rename and propagates mode, rename and credential-kind changes live to independent instances. File events are coalesced. Watch errors or unexpected watcher closure make state unavailable immediately. Reattachment is bounded to three retries by default, with configurable bounded delay; exhaustion stays unavailable until a new service is started. Missing or unreadable watchers never silently become an off setting. Subscribers receive generic snapshots only, and subscriber errors do not create logs or leak data.

Consumer obligations and exclusions

The record is an experience preference, not broker authentication, encryption, account authorization or protection from another person who controls the machine. Exit verification does not mint a broker capability or session. The bounded service currently has no complete durable lockout-budget/unlock-ladder integration; this remains required before presenting a full authentication/lockout experience.

Application and browser consumers remain separate work. Each must carry its own discoverable control, observe current mode and exact rename live, force English when active, and omit the disallowed language/humor/vocabulary/surprise controls, routes, search/palette results, previews and references. Preserve prior choices and validated private caches without applying them; restore them only after successfully verified exit. Do not infer inactive state when the service reports unavailable. An authenticated browser bridge requires scoped pairing and current-state handling; an independent origin-local Boolean is not a universal replacement.

Keep this shared record, credential references and protected verifier strings out of ordinary settings exports, snapshots, undo/history, synchronization, notifications, diagnostics, logs and telemetry. The private vocabulary cache stays separate and contributes no payload or imported-file metadata to this service. Only generic source, errors and generated neutral test data were used during implementation. No actual private dictionary or protected host credential was read.

Actual checks and limits

node --test tests/shared-mode.test.cjs passes twelve focused tests on Linux. They exercise two real fs.watch instances observing entry, rename, credential replacement and verified exit; restart and record deletion/reset; stale revisions; real child-process lock contention; bounded watch failure/retry and last-known rename; corrupt/foreign/duplicate/link/hardlink records; directory identity replacement; vault/passkey unavailability; lost lock ownership; failed atomic rename preservation; same-revision external edits and identical-byte inode replacement during verification; edits during temporary-file flush; and failed lock initialization cleanup/retry while preserving foreign replacements. Tests inject an in-memory vault to inspect service behavior; they do not prove OS-vault security or cross-product decryption. npx tsc --noEmit passes for the current repository. No GUI, companion bridge, universal existing-app adoption, native Windows, native passkey or full School mode acceptance is claimed.

Desktop host boundary

The desktop host supplies a common protocol directory below the user's local application-data root, Ding-Ding Projects/shared-experience-v1, with a separate protected credential directory. Windows uses the local application-data location; Linux development uses the user data directory. This is an explicitly selected protocol location for participating applications, not proof that existing sibling applications or different vault providers interoperate. The host uses Electron protected storage and refuses unavailable or insecure providers; native Windows and cross-product decryption remain unverified.

An explicit isolated verification profile uses its own verification-only mode directory. This prevents verification launches from inspecting or changing the user's real shared preference or credential store; evidence from that route cannot establish live cross-application propagation on the normal host.

The admitted packaged main frame reaches the service through studio:shared-mode. Requests use a bounded, duplicate-aware JSON parser and exact action schemas. PIN/password enrollment, verified exit, rename and revision checks stay in the host. Recovery information is a separate user-invoked read. Passkey transport is not exposed without an admitted provider. The bridge never logs requests, echoes credential input, or adds mode records to workspace exports/history. It returns generic bounded error codes and rechecks frame authority after both resolved and rejected asynchronous work. Live events carry only validated state snapshots, with configured/unconfigured/unknown consistency checks and no credential reference or hash. Shutdown unsubscribes watchers and closes the service; startup awaits the application URL load.

The host/core/preload checks pass 17 cases on Linux, including parser rejection, frame revocation during asynchronous success and failure, event validation and listener cleanup. The GUI controls, complete forced-English/suppression inventory and native protected-storage behavior have separate integration and acceptance requirements.
