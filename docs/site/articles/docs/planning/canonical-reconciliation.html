Canonical section reconciliation

The reconciliation index maps all 109 stable public identities and all 427 current planned requirement IDs to their canonical obligations and concrete missing details. It preserves the 436 surface records, existing work IDs, conditional dispositions and narrower canonical/owner-memory/product-inapplicable reasons. Identity and surface dispositions remain unchanged while the planned detail inventory expands. These are source and scope mappings, not full independently reviewed canonical acceptance or product delivery.

Source bindings and privacy

Each reference records its source document and an opaque SHA-256 of document#anchor, with the canonical revision recorded once for the inventory. Non-restricted feature documents additionally carry the complete section and document SHA-256. Restricted private instruction content digests are omitted: a public repository must not pin dictionary content or its derived lock digest. Public labels use ordinary feature names and contain no private dictionary, host path or user payload.

A reviewer with the canonical source resolves each catalogue link privately. Non-restricted section content runs from its heading to the next heading at the same or higher level and is hashed as UTF-8. The source revision and catalogue digest bind the review input. A locator or content hash establishes source identity/currency only; it never establishes that an implementation exists, a command ran or a capture depicts the requested behavior.

Direct requirement mappings

All 109 identities now have direct feature-clause mappings. Each of the 427 current requirement IDs retains its original public obligation and an additional specific missing-detail or evidence field. The first seven identities were mapped in batch 01; subsequent stable batches cover language/settings, appearance/motion, controls/navigation/locks, tools/website, build/release and repository records. See the consolidated mapping record.

The mapping explicitly includes late per-language voice enumeration; scheduled-setting timezone/DST, precedence and stale-response guards; shared mode/watch/rename/credential behavior; full per-element layer/state/motion consumers; advanced per-field regex workbenches; six lock policies and all input-route interception; real version-bound tool and host adapters; exhaustive model/tag discovery and conservative measured fit; offline packaged dependency discovery; and exact installer/release source bindings. Existing summary paragraphs are never treated as complete implementation or proof.

Two catalogue links initially name a broad instruction section rather than isolating their operative clauses. Following the actual release-production workflow locates the explicit original-icon and repository-specific operating-procedure requirements. Those transitive sources are recorded separately; an independent reviewer still needs to verify source-link precision and the full requirement interpretation.

Cross-contract and scope reconciliation

Every identity also has a related-feature and applicable universal dependency map. User-facing rows inherit actual localization, accessibility, Material controls, appearance/motion, per-control guidance, own search/regex/palette, state/history/export and evidence obligations. Process-only and excluded rows retain their reasons; a dependency edge neither activates a conditional requirement nor creates a fourth user-facing implementation.

The review follows the managed-model installer procedure, Minecraft research/descriptor/target references, project-profile authority/privacy rules and release-production/verification workflow where they add operative detail. Research catalogues remain incomplete for historical distributions and runtime support. Four server execution targets, each selected source/version and each platform boundary need actual consumers and independent evidence. No inventory or catalogue count proves those variants execute.

Eight explicit conflict records distinguish:

  • Current public-photo authority from older bundled/attached-photo prose.
  • Primary-operation outcomes from dedicated sensitive-mutation history guarantees.
  • Local verification from the prohibition on Actions quality gates.
  • Selected physical-host native work from fresh-environment bootstrap fixtures.
  • Windows desktop delivery from Linux execution backends/source previews.
  • Independent visitor features and authenticated mediation from a primary-runtime imitation.
  • Faithful exports from private-vocabulary and secret exclusions.
  • Exact source references from prohibited public dictionary-content digests.

The canonical offline-documentation and external-editor sections describe installed applications while the public ledger retains A/D/C obligations. Browser equivalents require explicit per-capability adaptation review. Installed-extension download handoff cannot be proven by a website simulation or update downloader. Onboarding retains its A-only identity without weakening separate website or contextual-guidance requirements.

Remaining acceptance work

The direct mappings and dependency graph are complete as planning records. Transitive referenced material is not exhaustively reconciled: detailed version-specific source/protocol research, full control/action/state/capability inventories, actual consumer/test/article/copy/persistence bindings and independent review remain open. The graph identifies obligations and conflicts; it does not mechanically prove they have been implemented or fully audited.

No identity was newly marked canonically accepted, no roadmap parent was completed and no product surface or native proof was promoted. Complete source/consumer reconciliation, independent review and genuine source/build-bound runtime evidence are still required before PH01-T01-C02 or any full feature acceptance can close. Native acceptance remains separate from this planning delta; inherited receipts are not upgraded by this inventory update, and account-dependent evidence still requires actual authorized access.
