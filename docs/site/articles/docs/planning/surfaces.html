Surface identities and capability boundaries

These are separate planned acceptance targets. Shared code is allowed, but every claimed feature needs its own state consumer, action route, article/copy, persistence and actual proof on each applicable surface.

ID Surface State and authority
A Installed Windows application Local stable application identity, OS-vault references, typed broker, actual WSL/Docker/host capabilities
D Public documentation visitor surface Public articles/downloads and full required interactive visitor-owned features; browser-local settings/history/locks/tools, no automatic host authority
C Authenticated browser companion Explicitly paired browser/device, scoped local or LAN broker capabilities, authenticated connection/revocation and its own client state
R Repository/operating/build/release records Source, planning and feature articles, native build/package/publication evidence and current handoff

Independent delivery

Expand each shared inventory row into A, D and C records before implementation. A documentation-site control that only redirects to C does not deliver its D row; a C control cannot be counted as a public visitor tool. Both browser surfaces remain actual task interfaces rather than command catalogues.

For each control, classify its consumer as browser-native, packaged-native, or typed broker action. Record capability discovery, pairing/permission needs, exact unavailable/disconnected/offline behavior and the admitted implementation. A website manifest or generic “connect desktop” button does not establish tool delivery. The public documentation home remains documentation/download presentation; it is never the installed application's primary runtime.

Visitor privacy

D keeps visitor-owned state locally with no analytics or uploaded personal vocabulary. Browser credential/history storage needs its own explicit implementation and reset explanation rather than an invented OS-vault claim. Private mappings, secrets and captures of usable credentials stay out of public records. Shared mode, locks and accessibility must each preserve their actual platform boundary.

C pairs through real authentication and explicit capability review. Experience locks are ornamental state, not the companion's authentication. Host credentials never enter browser source or public hosting. Revoking a client stops new authority and settles owned operations truthfully.

Evidence

Each D and C route has its own responsive/language/theme/scale and interaction inventory, actual persistence/reload proof and safe genuine captures. Local browser evidence cannot establish A's Windows installer, input or guest lifecycle proof. Runtime and hosted publication verdicts remain separate.
