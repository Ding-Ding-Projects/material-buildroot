Catalogue delta: file-drop wording and private documentation delivery

Status and source boundary

This is a bounded planning reconciliation against owner-contract revision 13b4fb30ddcd1c7a4af6989a985ceae43af4f0eb. It adds two public-safe identities and fourteen manually reviewed child requirements. The inventory now contains 109 identities, 436 independent A/D/C/R records and 412 requirements. All 398 earlier requirement IDs remain stable. Existing historical receipts and completed milestone counts are retained with their original scope.

New source correspondence uses opaque locators. Existing reference bindings retain their earlier revision rather than being silently relabelled as newly reviewed. This article contains no private source location or private identity spelling.

No new application behavior, runtime evidence, capture or completion acceptance is claimed. Focused inventory validation and independent review remain pending.

Application file-drop wording

vocabulary-drop-apply requires independent delivery in A, the installed application, and C, the authenticated browser companion. D, the public documentation visitor surface, is expressly excluded from this identity. Its existing Settings upload remains independently required. R records this feature's exclusion from an operating-process interaction; repository documentation and evidence duties remain independent.

The eight planned requirements cover:

  1. Drops anywhere within the application-owned surface, using the same bounded validator as Settings.
  2. Atomic immediate application, validated private local persistence and a working Settings fallback.
  3. Localized invalid, oversized and non-JSON rejection without changing prior state.
  4. A nonblocking full-window celebration with entrance, approximately three-second hold and exit.
  5. One headline derived from the supplied mapping, with a neutral localized fallback and no bundled private values.
  6. Reduced-motion behavior, polite assistive announcement, continued input and preserved focus.
  7. Shared-mode suppression and existing cache, privacy, no-network, export/history and reset boundaries.
  8. Independent built-surface interactions, omission regressions, restart/reset and genuine source-bound evidence.

A browser extension is part of the global rule's subject, but no new extension deliverable is introduced for this product. A companion page can receive events only within its own application-owned document, not unrelated browser controls. Any concrete capability limitation still needs its own documented and verified boundary.

The planned A and C consumer paths are reserved identities, not admitted implementation. Their source/build hashes and proof slots remain empty. The actual control, route, localization, persistence and test inventory must be reviewed before implementation.

Conditional private documentation package

private-documentation-package is a neutral public identity for a privacy-conditional delivery format. This repository is public, so A, D, C and R retain explicit not-applicable records for this identity. That exclusion does not waive public hosting, complete articles/wiki content, verified downloads or the exact About homepage.

The six planned requirements describe the inactive private condition:

  1. Private-only activation and preservation of the public hosting/homepage boundary.
  2. Complete offline home/download presentation, articles, wiki, categories and internal navigation with local assets.
  3. A dedicated static documentation viewer, without authorizing a primary runtime or public-delivery change.
  4. Existing root build/installer entrypoints, genuine Squirrel.Windows packaging and a normal verified release asset.
  5. Actual approved hidden-desktop installation or launch, route/inventory checks, no-network proof and genuine captures.
  6. Same-task maintenance and private release linkage without publishing private content to evade hosting limits.

No wrapper, installer target, release asset, hosting change or private-source publication is authorized or implemented by this reconciliation. If visibility changes later, applicability must be reviewed explicitly before activating consumers.

Existing identities and validation

Stable requirement IDs under landing-site, homepage-link, installer-download-button and wiki-site-sync receive narrow delivery-condition amendments. The documentation feature enumeration respects expressly excluded application-only identities; it does not turn the drop behavior into a visitor requirement. Personal-wording upload and its independent visitor implementation remain required.

The ledger, independent expected-subrequirement inventory, reconciliation and roadmap share the reviewed 109/436/412 totals. All 19 focused ledger cases passed, including negative cases for omission of either identity, waiver of the companion drop requirement, and activation of private documentation delivery for the current public product. Independent clause/surface review found no introduced gap in this bounded reconciliation. This is planning-artifact evidence, not complete semantic admission or product implementation.

Configuration, failure modes and next steps

No runtime setting or HTTP API is introduced. Postman collections are not applicable to this planning article. Invalid or stale catalogue bindings, missing identities and unsupported surface dispositions must remain validation failures, not optimistic completion records.

Source-bound documentation publication remains a separate pending operation. Application implementation and private-format activation remain outside this planning change.
