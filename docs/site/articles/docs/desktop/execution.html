Project execution adapter

src/main/execution/index.cjs is a main-process adapter with an accompanying TypeScript declaration. It is not an IPC dispatcher and does not authorize renderer-supplied paths. The host must obtain a native project grant and explicit consent to execute the selected source before calling grantProject({root, source, output, trustedSource: true}). These directories must already exist. Source and output must be separate, non-overlapping directories within the granted canonical root; a source Makefile is required. Build paths currently accept only ASCII letters, digits, separators, colon, dot, underscore, plus and hyphen; spaces and make/shell metacharacters are rejected, including $ expansion in make variable values. Unsupported paths require an explicitly chosen compatible location, never automatic relocation. The adapter never deletes or provisions distributions, images, source trees, output trees or volumes.

discover() probes Docker server OS and installed WSL distributions with a ten-second timeout and 64 KiB output limit. Missing tools return unavailable; non-Windows WSL discovery returns unsupported-platform. Discovery does not install dependencies or launch builds.

start({grantId, runtime, target, jobs}, onLog) revalidates canonical directories and filesystem identities, then returns {completion, cancel}. Targets are an explicit enum: all, olddefconfig, savedefconfig, legal-info, source, show-info, and graph-depends. Destructive clean targets and arbitrary make arguments are unavailable. Jobs range from 1 to 64. Concurrent work sharing the same source or output is rejected within the service instance; the host should retain one instance and use the durable job scheduler for global admission, revision binding and cross-project resource accounting.

Docker accepts an explicitly selected digest-pinned image and numeric non-root UID/GID. An absent pinned image fails instead of triggering an automatic pull. Builds use an owned random container identity, dropped capabilities, no privilege escalation, no network, 512 PIDs, two CPUs and 4 GiB memory. The existing source is mounted read-only and existing output writable. No host credentials or Docker socket are mounted. Cancellation stops only the task-owned container; cleanup failure is a distinct result. Networking is intentionally unavailable in this bounded adapter, so fetch-dependent builds need prepopulated sources or a future explicitly admitted fetch operation. Docker-managed named volumes and permission-repair workflows remain pending; these bind mounts do not prove their implementation.

WSL accepts an explicit distribution name and translates the canonical host directories through wslpath. The fixed Linux launcher checks a non-root effective UID and runs make in an owned setsid session. Its first output line identifies that session for targeted TERM/KILL cancellation; later source output cannot replace that identity. Missing setsid, make, wslpath, or non-root configuration causes an actual failed result. Distribution provisioning, Linux-side managed storage, Windows permission/reparse acceptance and current Windows WSL behavior remain unverified. Existing Windows-mounted paths can be slower than Linux-side storage.

All launch arguments are separate argv entries with shell:false. The only shell program is fixed source code with positional path and target arguments. This prevents renderer command interpolation; custom Makefiles still execute arbitrary source-controlled build logic with the selected runtime user's authority. Non-root execution and container restrictions do not make untrusted source safe. Source consent and revision/source locks are host obligations. Configuration argument plumbing and scoped terminals remain pending.

Logs are streamed through the callback and retained up to a combined 16 MiB. Exceeding that bound cancels the job with output-limit; builds have a 24-hour timeout. Cancellation, timeout and output overflow use owned process/container cleanup. A failed remote cleanup returns runtime-cleanup-failed, requiring explicit host recovery rather than a success claim. OS process-group cancellation cannot restrain deliberately escaping trusted-source processes, and no app-restart reconnection claim is made. Durable logs and recovery belong to the host job manager.

Verification: node --test tests/execution.test.cjs passes eighteen local Linux tests covering argv preservation, target/root rejection, path and symlink escape, grant replacement, bounded missing-tool discovery, output limits, timeout, cancellation and Docker argv isolation and cleanup-failure fixtures, and a genuine non-root make fixture producing an output file while preserving source. The fixture adapter is enabled only by a main-process constructor option and is not a Windows runtime. No WSL build, Docker daemon build, Buildroot image, Windows execution, managed GitHub Actions job or native UI capture was exercised. PH05 remains open.

Source acquisition and reviewed upgrades

source.cjs exports SourceService. The host grants an existing canonical parent using grantRoot(root); clone and adopt accept a single validated child directory and require trustedSource: true. Clone refuses nonempty destinations and symlinks, disables recursive submodules, uses detached immutable commit checkout, and preserves partial destinations on failure. Production URLs must be HTTPS without embedded credentials, query strings or controls. Local filesystem transport is available only through the host-only allowLocalFixture constructor option. An absolute Git executable can be selected by the host; executable paths, transport options and lock callbacks must never come from renderer requests.

Git commands use separate argv entries, disable system/global Git configuration and credential helpers, disable prompting, disable source hooks, and admit only HTTPS transport. Existing trusted repository configuration and build logic remain part of the explicitly trusted source; this adapter does not sandbox Git itself. Private-source credential enrollment, archive downloads and LTS catalogue recommendations remain separate work. Commands have a ten-minute timeout and 4 MiB result bound; interrupted clone data is retained rather than automatically removed.

status(projectId) reports the actual commit, current branch or detached state, tracked/untracked/submodule changes and dirtiness. acquireRef fetches an explicitly named ref without changing the checkout. previewUpgrade requires a full immutable commit ID and returns a bounded diff, current dirty state, and an explicit unknown output compatibility verdict. applyUpgrade requires that preview, expected original commit and explicit consent. It refuses dirty or changed source and changes only the checkout; existing outputs stay untouched. It returns the prior immutable commit for a separately previewed rollback. Branch refs, untracked content and source edits are preserved. No compatibility, snapshot or configuration migration is inferred from successful Git checkout.

An upgrade also requires the host acquireSourceLock(canonicalSource) callback to return a release function. It must atomically exclude active execution and source editing across the host services; missing or denied ownership fails closed. The service additionally serializes its own mutations. Native filesystem reparse/race acceptance, externally modified source during Git operations, durable preview recovery and real interrupted-network acquisition remain pending.

node --test tests/source.test.cjs passes six real local Git fixture tests for clone provenance, exact fetch, immutable preview/apply/rollback, dirty tracked and untracked preservation, unsafe protocol/ref/path rejection and source-lock denial. These fixtures neither fetch the public network nor prove current Windows Git behavior.

Managed GitHub Actions adapter

actions.cjs exports ActionsService, generateWorkflow, validateExpertWorkflow and createGitHubTransport. The host injects an OS-vault credential callback, then explicitly selects an execution repository and workflow name. No repository creation, workflow write, credential persistence, deployment, release or publication happens automatically. Standard hosted execution is limited to ubuntu-24.04. Self-hosted Linux/X64 selections require explicit labels and billing consent, and workflow review checks for a compatible online runner. Larger hosted runner labels are rejected.

The generator produces a fixed Buildroot workflow using commit-pinned checkout/upload actions, read-only repository permissions, non-root checks, a validated named target, explicit source repository and defconfig, immutable source revision input, no persisted checkout credentials, bounded job time and uploaded output. This is a real workflow body; the adapter does not install it into a repository. Runner prerequisites, source licensing and selected-source trust remain host admission responsibilities. Hosted/self-hosted Buildroot runtime compatibility has not been exercised.

Expert validation recognizes only the exact generated grammar, with CRLF normalization. It rejects arbitrary YAML, anchors, additional actions, permission edits and shell edits. It is intentionally not a general YAML parser. Editing supported settings requires a new typed model and review. reviewWorkflow resolves the selected workflow ref and reads the remote file at that exact commit; dispatch requires matching reviewed bytes and rechecks the ref. GitHub dispatch accepts a branch/tag ref, so a repository owner can still move that ref between verification and dispatch. Use a protected dedicated ref and trusted repository; observed runs with a different workflow commit are rejected, but this does not retroactively prevent external ref mutation. No immutable-ref guarantee is claimed.

Explicit dispatch returns a correlation operation ID, not an invented run ID. observe searches that workflow for the exact operation title, then validates the actual run and workflow revision. An unobserved queue stays awaiting-run. jobs reads actual job/runner state; cancellation returns cancel-requested until subsequent observation confirms the real outcome. receipt contains no token and can be stored by the host durable job manager; reconnect validates the saved operation/run/revision against the selected repository before restoring observation. Discovery, runner lists and job lists are bounded, with truncation reported; run discovery currently covers the latest 100 dispatches and may need retry or a saved receipt under heavy traffic.

Artifact download checks that the selected artifact belongs to the observed run, verifies its exact compressed size and caller-supplied SHA-256 (including the API digest when present), writes an exclusive partial file, then links the verified file without overwriting an existing destination. ZIP extraction is intentionally separate. The destination must already be resolved from a host save grant; raw renderer paths are not authority. Failed/truncated transfers remove only their owned partial file. The production fetch transport enforces time/output limits, follows only signed Azure artifact-storage redirects and strips API credentials on redirected requests. Other storage providers fail explicitly pending admission. Credential-bearing transport errors are replaced with bounded public errors.

node --test tests/actions.test.cjs passes nine mock-protocol tests covering workflow effects, runner billing restrictions, read-only discovery, remote byte review, dispatch ownership, cancellation, reconnect receipts, artifact verification, truncation cleanup, redirect credential stripping and hostile redirects. No authenticated GitHub request, hosted build, billed runner, repository mutation or live artifact download was performed. These tests prove protocol handling rather than a completed managed-build runtime record.

Host source operation integration

createSourceOperations in src/main/source-operations.cjs wraps the source backend in exact-field requests and bounded public error codes. Construct it with host callbacks chooseDirectory(), resolveWorkspace(workspaceId), onSourceAdopted({root, source, revision, branch}) and acquireSourceLock(canonicalSource). The picker returns an existing native-selected parent directory or cancellation. The workspace resolver must return only an authorized, previously trusted workspace {source}. The registration callback receives the canonical selected parent as root, preserves pre-existing output trees, and may reject with code: "ADOPTION_REQUIRED" while retaining the clone. It returns {workspaceId} after retaining the selected source in the host project store. The lock callback must atomically exclude builds and configuration/source mutations and return its release function; reject with code: "SOURCE_BUSY" when unavailable. Constructor sourceOptions are host-only dependency settings, never renderer data.

Call handle with these action-specific fields (besides action):

Action Fields
source.choose none
source.clone selectionId, single child directory, HTTPS url, ref, trust: true
source.status workspaceId
source.ref workspaceId, ref
source.upgrade.preview workspaceId, immutable revision
source.upgrade.apply workspaceId, previewId, expectedRevision, consent: true
source.rollback.preview workspaceId, rollbackId from a successful Apply
source.rollback.apply workspaceId, rollback previewId, expectedRevision, consent: true

Replies are {ok: true, ...result} or {ok: false, code}; raw errors, subprocess stderr and filesystem paths are not returned by clone/selection. Preview handles are bound to their workspace, expected source revision and upgrade/rollback kind. Rollback requires its own fresh diff preview and explicit Apply. Unknown fields, including renderer paths or commands, are rejected. Clone destinations are never cleaned up automatically, including after failed host registration. HTTPS Git clone is the source download route; archive download is not offered here. Grants, previews and rollback receipts are session-scoped; restart requires host re-adoption and a new preview.

node --test tests/source-operations.test.cjs passes four real local Git fixture checks covering registration-conflict preservation, host-selected clone/fetch/upgrade/rollback and negative request authority, trust, foreign preview, stale revision, missing consent, dirty preservation and build-lock denial. These checks do not exercise Windows or live network access. Main-process operation dispatch and renderer wiring are separate integration work.

Ordered external build trees

The host may pass externalTrees: string[] to grantProject, with an empty-array default. A nonempty array additionally requires trustedExternalTrees: true, representing explicit consent to execute those selected external trees. This is host filesystem authority: renderer paths must first pass the native selection/admission boundary. Regranting validates the complete replacement before adding a new grant; failed validation does not revoke an existing grant.

At most 32 unique canonical directories are accepted, in the supplied order. Each requires ordinary non-symlink external.desc, Config.in and external.mk files. Aliased paths, unsafe build path characters, list-separator colons outside a Windows drive prefix, and overlap with the output tree are rejected. External trees may be independently host-selected outside the project root. The adapter records directory/descriptor filesystem identities and revalidates them before execution, including after asynchronous runtime path translation. Missing, replaced or symlinked descriptors fail with external-path-changed. This checks file authority and existence rather than claiming full Buildroot descriptor semantics or immutable package content.

The fixed launcher passes one BR2_EXTERNAL=... make argument; the renderer cannot supply make variables or launcher options. Linux fixture execution uses the canonical ordered paths. WSL translates each tree individually and rejects unsafe translated paths. Docker binds each selected tree read-only at /external/0, /external/1 and so on, and passes that ordered colon-separated container path list. An empty list explicitly passes BR2_EXTERNAL=. Tree activation preserves the existing source/output/cancellation behavior; runtime source locking still belongs to host admission.

Four additional focused Linux checks cover external consent/count/duplicate/descriptor rejection, failed-regrant preservation, descriptor replacement/deletion rejection, exact Docker mount/list argv and a real non-root make fixture receiving the ordered external list while preserving descriptor contents. node --test tests/execution.test.cjs passes all eighteen checks. No native WSL or Docker daemon execution was performed for this change.

Runtime compiler environment

probeEnvironment({grantId, runtime}) returns typed {hostArchitecture, hostGccVersion} from the selected runtime's actual gcc -dumpmachine and gcc -dumpfullversion -dumpversion. It accepts no caller command, script, environment or compiler arguments. The architecture comes from the compiler target’s first component, following Buildroot aliases (i.86 → x86, sun4u → sparc64, arm*/sa110 → arm, ppc64 → powerpc64, ppc/macppc → powerpc, sh* → sh), rather than the running kernel architecture. The full observed GCC version is retained; the configuration consumer derives Buildroot's required major-version value separately. Project and external-tree grants are revalidated before and after probing. Missing tools, malformed output, expired grants and root execution fail explicitly rather than supplying guessed host values.

Docker probes use the same digest-pinned cached image and non-root UID/GID selection, with no project mounts, a read-only container filesystem, no network, dropped capabilities and bounded CPU/memory/PIDs. Timeout cleanup stops only the owned probe container. WSL probes use the selected distribution with a fixed Linux-side eight-second timeout and one-second kill grace; missing GNU timeout is an explicit prerequisite failure. The outer process has a ten-second bound and 4 KiB output limit. Linux fixture probing requires its host-only admission flag and a non-root account.

Two focused checks exercise exact Docker probe argv, normalized/invalid output, root/arbitrary-field rejection, revoked grants and actual architecture/compiler discovery under a non-root Linux account. A further compiler-target fixture checks twelve mapped and unchanged target cases. The execution suite now passes eighteen tests. These checks do not establish WSL, Docker-daemon or native Windows runtime compatibility.

Concurrent durable build scheduling

createBuildScheduler in src/main/jobs/scheduler.cjs schedules the existing durable job manager instead of replacing its ownership, cancellation, retry, log or restart records. The host supplies one scheduler and the same job manager instance. It must enqueue a durable payload.intent with {projectId, sourceRevision, configRevision}. These revisions are meaningful host evidence of source/configuration content, such as an admitted source-service revision plus a bounded all-source dirty snapshot and the authoritative configuration revision. Directory identities or unchanged paths are not content revisions. Capture before enqueue and preserve the original intent across retries; never silently replace it with current source on dispatch.

The host resolveAdmission(job) verifies that persisted intent against current content and resolves canonical authority into {projectId, source, output, externalTrees?, resourceDomain, storageDomain, cpuSlots, memoryBytes, storageBytes, intent: {sourceRevision, configRevision}}. The scheduler compares intent and validates existing canonical directories. It resolves admission again while its source/output/external leases and optional host acquireLease(admission) are held, preventing a stale observation from bypassing the intent check. The host must use these same leases for configuration, package and source mutations. Root dispatch integration is separate from this backend unit.

observeResources(admission) returns {resourceDomain, storageDomain, cpuSlots, memoryAvailableBytes, storageAvailableBytes}, with null for unavailable measurements. Domain keys identify shared capacity, not individual jobs: projects in one Docker/WSL runtime must share their resource domain, and output directories on the same filesystem share a storage domain. Unknown metrics keep work queued as BLOCKED_RESOURCE_UNKNOWN. Explicit limits contain global {maxConcurrent, cpuSlots, memoryBytes, storageBytes} budgets; positive CPU/RAM claims and nonnegative storage claims are admission reservations supplied by the host, not measured build requirements or promises about future usage. Observed availability additionally constrains each runtime/filesystem. Memory measurements already consumed by active builds are conservatively combined with reservations; resource usage can change after observation.

pump() scans at most maxScan queued records, rotating its scan window between calls. Only each project's earliest queued job is eligible, while independent projects may run concurrently. Project, source, output and external-tree leases exclude ancestor/descendant overlap even between different projects. acquireMutationLease({projectId, source, output, externalTrees?}) returns an idempotent release function or throws SOURCE_BUSY. Host leases and reservations remain held through actual job completion, including asynchronous cancellation cleanup. Releasing a mutation lease requests another scheduling pass. Capacity or external changes require the host to call pump() again; no unbounded background polling occurs. Host admission/observation/lease callbacks have a fifteen-second default bound (callbackTimeoutMs, at most sixty seconds); timeouts leave work queued with BLOCKED_ADMISSION_TIMEOUT, and a late host lease is immediately released.

status() reports running reservations and actionable queued block reasons without host paths. awaitIdle() waits for current scheduling/running work, and may return with blocked queued work. close() stops new admission and preserves queued jobs; it does not cancel active jobs. Host shutdown can explicitly cancel jobs through the existing job manager and then await cleanup. Reloaded queued jobs require a new host-validated scheduling pass; interrupted jobs remain interrupted rather than replaying automatically. An unexpected run-start failure is quarantined for that scheduler instance rather than repeatedly retried.

Nine focused scheduler checks verify independent concurrency/project FIFO, CPU/RAM/storage/unknown admission, reservation retention through cancellation cleanup, ancestor/external-tree mutation exclusion, close/restart queue preservation, cancellation races, immutable intent revalidation under host lease, bounded scan fairness lease-denial recovery and bounded admission callback timeouts. These checks use the real durable job manager with controlled adapters; they prove scheduler behavior rather than real build resource consumption.

Runtime resource observations

probeResources({grantId, runtime}) returns {cpuSlots, memoryAvailableBytes, storageAvailableBytes, observedAt, constraintModel}. Each metric is a nonnegative safe integer or null. Fixed non-root commands read the process affinity CPU list, visible cgroup-v2 ancestor CPU quotas and memory limit/current counters, Linux MemAvailable, and output-filesystem df -Pk available bytes. Unsupported cgroup v1, inaccessible hierarchy or unresolved namespace paths leave CPU/RAM explicitly unknown. Fractional CPU quotas are conservatively rounded down to whole admission slots. No fallback host guesses are supplied.

Docker probes retain the selected cached digest-pinned image and non-root identity, fixed two-CPU/4 GiB execution envelope, dropped capabilities and no network. Only the selected output directory is mounted, read-only, to measure its actual filesystem. A host cgroup namespace is selected for read-only hierarchy visibility; unsupported Docker policies fail explicitly. WSL probes translate only the granted output path and use fixed Linux-side timeout/kill grace. Both have a ten-second outer timeout and 4 KiB output bound. Root and external identity checks run before and after probing. These observations support admission reservations; they neither enforce a WSL memory quota nor prove that a future build fits its reservation.

Two added execution checks verify Docker read-only output argv, explicit unknown values and actual non-root Linux filesystem observation without writing output. No native WSL, Docker daemon or Windows resource measurement was exercised. The focused execution/scheduler command is node --test tests/execution.test.cjs tests/build-scheduler.test.cjs.

Desktop queue integration

The desktop operations service now submits builds to the durable scheduler. build.submit accepts the existing exact {workspaceId,target,runtime,jobs} arguments and an optional exact resources:{cpuSlots,memoryBytes,storageBytes} object. It returns the accepted durable queued job, rather than claiming execution began. A scheduling pass resolves current native authority, checks the original content intent, obtains actual probeResources observations, acquires source/output/external-tree leases and rechecks content before dispatch. An unavailable runtime or unknown capacity leaves the job queued with a reason. There is no direct-start fallback.

Legacy callers reserve at least two CPU slots, 4 GiB memory and 8 GiB storage. WSL reserves max(2,jobs) CPU slots by default; explicit CPU reservations must cover the requested make parallelism. Docker reserves at least its full fixed two-CPU/4-GiB execution envelope, irrespective of make parallelism. Explicit CPU reservations range through 64 slots; WSL memory reservations range from 256 MiB through 256 GiB, Docker memory reservations from 4 GiB through 256 GiB, and storage reservations from zero through 1 TiB. Invalid or extra resource fields are rejected. These are explicit admission budgets, not measured requirements, output-size estimates or new runtime arguments. A zero storage reservation explicitly removes that admission free-space floor; it does not mean the build writes no data. Source/output preservation and actual filesystem failures remain independent.

The host's default global policy allows at most four concurrent builds, 32 reserved CPU slots, 32 GiB reserved memory and 128 GiB reserved storage. Trusted host construction may supply another validated policy. One conservative local runtime resource domain combines reservations across the supported local runtimes; output storage domains use the host filesystem device identity, so projects sharing a volume share reservations. Actual runtime observations additionally constrain admission. The Docker probe reports shared parent/VM capacity after verifying and excluding only its own artificial two-CPU/4-GiB probe leaf; real inherited limits remain effective. This does not aggregate independent per-container quotas into invented host capacity. WSL reservations do not impose operating-system CPU or memory quotas, and no admission result promises future memory use, physical host capacity or successful build completion.

jobs.pump with exact {} arguments requests another bounded scheduling pass after capacity, runtime or authorization changes. scheduler.status with exact {} arguments returns {closed,running,blocked,reservations,counts,limits,defaultReservations}. Running entries contain job/project IDs and reserved resources; blocked entries contain job IDs and reason codes. Neither surface returns host paths or source bytes. Representative reasons are BLOCKED_RESOURCE_UNKNOWN, BLOCKED_CPU_LIMIT, BLOCKED_MEMORY_LIMIT, BLOCKED_STORAGE_LIMIT, BLOCKED_SOURCE_BUSY, BLOCKED_PROJECT_FIFO, BLOCKED_INTENT_CHANGED, BLOCKED_AUTHORIZATION_REQUIRED and BLOCKED_EXTERNAL_AUTHORIZATION_REQUIRED. Capacity observations must carry a fresh timestamp; unavailable, malformed or stale observations never become guessed capacity. There is no continuous polling loop.

Same-project queue order is retained while independent nonoverlapping projects may run concurrently. Active source/output/external-tree leases and reservations last through actual completion, including cancellation cleanup. Configuration writes, runtime preference changes, ordered external-tree activation, package operations and source clone/ref/upgrade/rollback operations use the same ancestor-aware leases. A clone into a not-yet-existing directory conservatively leases its existing selected ancestor. Guest/conversion operations that mutate project output also obtain project leases. Artifact and guest inspection remain available. These checks coordinate the admitted operations service; they do not claim filesystem isolation from unrelated applications or from arbitrary code deliberately executed by a trusted source/runtime. Separate server/tool processes and arbitrary external editors are not converted into managed build jobs by this integration.

Content-bound build intent

src/main/jobs/build-intent.cjs captures deterministic aggregate receipts over ordinary source files, ordered active external trees and the output .config. Directory paths or inode identity alone never stand in for content. The source digest includes relative entry names, file permission modes, complete regular-file byte hashes, literal symbolic-link bytes and bounded Git HEAD/ref/packed-ref/shallow receipts. Git config, hooks, logs, index and object history are excluded, and their bytes are never put in a job payload. Malformed non-UTF-8 entry names fail explicitly rather than aliasing decoded names. Current Git ref-only changes therefore invalidate intent without retaining repository history or credential-bearing configuration. The configuration digest distinguishes a missing .config from its actual bytes.

Persisted snapshot metadata is version 2 with {version,entries,bytes,excludesGitObjectHistory:true,symlinkPolicy:"link-text-only",symlinks,limitations:["SYMLINK_TARGETS_OUTSIDE_CAPTURED_FILE_NAMESPACE_ARE_NOT_BOUND"]}. Only hashes, counts, this policy and the explicit limitation leave the helper. It never returns or persists source file contents, a path inventory or symlink destinations. Runtime selection and explicit reservations remain separate typed payload fields.

The link-text-only policy supports Buildroot filesystem-template links, including absolute paths that describe the target system. The helper reads link text and identity without resolving, traversing, copying or reading the referent. Ordinary in-tree target files are independently hashed when encountered through the ordinary file namespace. Referents outside that namespace are explicitly not immutable captured inputs. Link text grants no authority over another host path. Native source-execution consent remains necessary because a custom Makefile can execute source-provided logic; this receipt is not a sandbox or a complete reproducibility lock for every file a custom build could consult. Git reference metadata, project/configuration roots and selected external-tree authority retain stricter canonical/link checks.

Capture is bounded to 50,000 entries, 512 MiB of total read bytes, 64 MiB per file, depth 64 and ten seconds. Directory enumeration consumes the same global entry budget. The helper reads files through bounded buffers with no-follow open flags where available, verifies descriptor identity after opening and reading, rejects multiply linked regular files and rechecks captured identities before returning. Corrupt, changing, unsupported or excessive inputs fail explicitly without modifying source/output or substituting weaker identity evidence. Roots and configuration files cannot be symbolic links; selected external trees require current native handles before content inspection. These are optimistic filesystem checks, not atomic compare-and-swap protection against a hostile replacement after the last check.

Every queued job retains its original {projectId,sourceRevision,configRevision} across retries. Changes leave it blocked; jobs.retry never silently captures current source as the old intent. An explicit new build.submit constitutes a new content-bound submission. Reloaded records have no persisted authority: native project adoption and renewed external-tree selection/activation must occur before probing or execution. Old records lacking this admitted intent remain blocked rather than being upgraded through a path-only fallback. Shutdown stops admission, preserves queued records, cancels active owned jobs and awaits actual cleanup; cancellation during pre-execution hashing cannot cause a late launch.

Focused host/hash fixtures cover actual durable-manager integration with controlled execution adapters: independent concurrency, FIFO, unknown and insufficient observed capacity, explicit reservations, stale source/config/external content, unchanged retry intent, restart reauthorization, ancestor/source/config/package/external mutation exclusion, cancellation/disposal cleanup and input preservation. A read-only capture of official Buildroot 2025.02.1 succeeded with 19,423 entries, approximately 22.2 MB of captured content and 181 literal symbolic links in approximately 4.5 to 5.3 seconds. This proves source capture compatibility for that source state, not a Buildroot build. Native Windows, WSL and Docker-daemon execution remain unverified in this integration unit.

Durable cleanup quarantine

The operations host writes a pending recovery record before requesting runtime startup. Execution ownership checkpoints are awaited before build effects: Docker binds an operation token and owned container name to the observed daemon identity; WSL binds a distribution, boot identity and PID namespace, then the owned session PID and process start time before releasing its fixed startup gate. The adapter revalidates live grant authority, directory and external-tree identities, and cancellation after the final awaited checkpoint and immediately before startup authorization. Rejected pre-spawn authority does not retain source/output locks. Recovery records contain bounded identities, job/workspace IDs and timestamps, never source bytes, credentials or host paths. The journal admits at most 1,024 unresolved records and 1 MiB of serialized data; reaching either limit fails closed without pruning existing records. They grant no authority. Invalid, foreign, oversized, duplicate-key, multiply linked, symbolic-link or unexpectedly changed recovery storage is preserved and fails closed. JSON parsing is bounded to 1 MiB and nesting depth 16, with duplicate decoded keys rejected at every object level.

A typed RUNTIME_NOT_STARTED preflight failure proves that no owned runtime was spawned and clears its pending record as a failed job. Ownership-checkpoint failures are excluded from that proof and remain fail closed.

An unverified cleanup result is an interrupted job even when cancellation was requested. It must not appear as a successful cancellation. Its durable quarantine survives application restart, blocks all new build admission because shared runtime consumption is unknown, and denies mutations overlapping its saved project source, output or external-tree descriptors. The descriptors serve only as denial evidence, never fresh filesystem authorization. Independent inspection remains available. Native project adoption and reauthorization of the same ordered external paths remain possible; changing those paths while quarantined is rejected. There is no automatic expiry or timer-based lease release.

scheduler.status additionally returns quarantine:{unavailable,records:[{jobId,workspaceId,reason}]} and quarantinedReservations:{cpuSlots,memoryBytes,storageBytes}. These are separate from the scheduler's actively running reservation totals. Reasons are RUNTIME_CLEANUP_UNVERIFIED or RUNTIME_IDENTITY_UNAVAILABLE; new admission reports BLOCKED_RUNTIME_RECOVERY_REQUIRED. These summaries expose no runtime ownership receipts or host paths. A missing reservation on an older interrupted record is not interpreted as known free capacity.

The exact desktop action jobs.reconcile accepts only {id}. It requires renewed native project and external-tree authority, a read-only ownership check returning verified-stopped, and fresh, known CPU, memory and storage observations before clearing the durable record and requesting another scheduling pass. An unavailable runtime, changed daemon/distribution namespace, reused identity, missing precise ownership checkpoint or unknown capacity preserves quarantine. Renderer assertions, arbitrary PIDs, paths, ownership receipts and manual “assume stopped” flags are not accepted. Reconciliation does not kill an arbitrary runtime, reconnect an old build or mark the interrupted job successful; a retry still retains its original content intent.

Linux fixtures exercise journal persistence and preservation, cancellation with unverified cleanup, restart reauthorization, admission/mutation blocking, missing ownership, failed recovery, unknown capacity and explicit verified recovery. Real Windows/WSL/Docker runtime recovery remains unverified. Deliberately escaping source-controlled processes and externally restarted runtimes remain outside the owned-session/container model.

Queue controls in the desktop workspace

The Builds workspace now exposes separate Inspect queue and Recheck admission actions. Inspection reads current limits, counts, active reservations, quarantined reservations and blocked reasons. Rechecking can start eligible queued work. The submission form accepts CPU, memory and storage reservations through typed host fields; displayed job details retain the captured target, parallel jobs and source/configuration identities rather than silently substituting current project content.
