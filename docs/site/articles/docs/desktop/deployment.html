Artifacts and deployment

src/main/deployment/index.cjs exports createDeploymentService. The main process supplies an approved artifact root, optional executable paths and explicitly enrolled adapters. The renderer receives artifact-relative names and opaque operation identifiers. It cannot select an executable, URL, credential, SSH command or physical drive writer.

Implemented operations

The artifact browser lists files without following directory symlinks. Inspection rejects resolved paths outside the root, streams SHA-256, bounds text previews to 8 KiB and reads at most 1 MiB of format metadata. It identifies raw MBR/GPT disks, ISO9660, VDI, VMDK, qcow2, tar, zip, gzip and xz signatures. Partition metadata assumes 512-byte sectors; it reports partition ranges without mounting or executing an image. GPT arrays outside the inspected window remain unavailable. Archive recognition does not imply extraction or archive integrity validation.

Manifests sort selected paths and hash their bytes, with optional explicit source, Buildroot, configuration, toolchain and environment locks. Repeat-build comparison reports added, removed and changed outputs and lock changes. Byte equality covers only selected files. collectCompliance collects Buildroot legal-info files and checksums, bounded CSV previews and an SPDX file inventory with NOASSERTION licenses. It does not infer legal conclusions or claim a complete package SBOM.

VirtualBox discovery invokes VBoxManage --version; VMware discovery invokes vmrun -T ws list, which proves command availability but does not establish the installed Workstation version. Guest creation, editing, launch and graceful stop use fixed argv. Guests are scoped to an owned UUID and managed directory, and a registry retains incomplete provisioning for recovery. Production wiring must supply a host-owned persistent managed directory outside build output; the default is an isolated temporary directory and does not support restart recovery. NAT is the default. Hardware supports CPU count, memory and BIOS/EFI. Disk attachment copies an approved disk into the guest directory and verifies its hash, preserving the original image. VMware VMDK inputs must have been produced by the service's current conversion session. A stop request remains shutdown-requested until refreshGuest observes power-off; no forced power-off is offered. Native guest boot and shutdown remain unverified.

The topology API exposes four NIC slots and four media slots per guest. networks contains {slot: 1..4, mode: nat|none|bridged|hostonly, interface?}. VirtualBox bridged and host-only interfaces must be selected from the current discoverNetworks inventory; VMware uses Workstation's default bridged or host-only virtual network and does not offer explicit interface selection. storage contains {slot: 0..3, kind: disk|iso, artifact}; ISO attachments require an ISO9660 signature. Disk inputs require independent media without backing files, encryption or snapshots. Editing applies actual VirtualBox SATA attachment/detachment commands or the owned stopped VMware VMX. Detached copies remain on disk for preservation. createDiskArtifact({outputName, format: vdi|vmdk, capacityMiB}) creates an independent blank disk with fixed qemu-img argv, bounds capacity to 64–1,048,576 MiB, verifies a host-owned temporary output and exclusively copies it into a previously absent artifact basename. The new VMDK is admitted for subsequent owned-guest attachment. The canvas may derive stable node identities from guest ID plus NIC/media slot; moving a canvas node changes layout only.

previewGuestEdit({id, expectedRevision, hardware?, networks?, storage?}) returns an expiring previewId, exact next managed configuration and current revision. editGuest({id, expectedRevision, previewId}) consumes that plan once. Supplied arrays replace all slots; omitted arrays preserve the configuration. Preview and apply check actual stopped state, current interface inventory and source/copied media hashes. Application also checks the host configuration fingerprint captured by preview. Per-guest operation locks reject concurrent application and revisions reject stale consumers. A partial CLI failure produces configuration-unknown; observing a power-off does not clear that state. An explicit successful configuration reapply is required before launch. Legacy registries that contain only the earlier diskName field reject configuration edits until their storage is reimported; this prevents silently dropping a legacy attachment. Returned fields describe the configuration applied through the adapter, not verified guest hardware or boot behavior.

Conversion previews bind input SHA-256 and an absent destination. qemu-img info rejects backing files, encryption and snapshots; fixed-format conversion runs in a temporary directory and links the completed output only if the destination remains absent. Supported source inputs are raw disk, VDI and qcow2, with raw/VDI/VMDK/qcow2 output. ISO authoring and OVA/OVF appliance import are unavailable. Disk-based guest creation is the supported import route.

Adapter enrollment

Cloud adapters accept only host-enrolled HTTPS upload and readback endpoints on an explicit host allowlist. S3-compatible, Azure Blob, GCS and GitHub Releases use object-specific signed URLs/SAS or host-side scoped authorization callbacks. Enrollment supplies the already selected object and, for GitHub, the exact upload endpoint and method. The app does not discover accounts, issue cloud credentials or create releases. Azure adds x-ms-blob-type: BlockBlob. S3 and GCS attach SHA-256 metadata. Upload previews contain no URL or credentials, expire after five minutes and bind local bytes. Redirects fail closed. Success requires downloading the object and matching exact byte count and SHA-256; an accepted upload response alone is insufficient. Abort signals reach upload and readback. A retry requires a fresh preview; partially uploaded provider state may require provider-side cleanup.

Remote adapters are an explicit transport boundary for the fixed material-buildroot-v1 subsystem. Enrollment fixes the host, port, credential reference, approved Linux process/Docker or Windows WSL/Docker kind and SHA-256 SSH host fingerprint. The injected transport must enforce that fingerprint before opening the subsystem and report the observed key. Typed capability/start/observe/cancel messages carry manifests and fixed build targets. Only jobs created by the service can be cancelled. The subsystem transport, remote helper deployment, manifest transfer, durable reconnection and downloaded output verification are not implemented here; no real SSH execution is claimed.

Flashing requires an explicitly admitted platform adapter. Preview inspects the exact device identity, capacity, mounted/system state and image hash. Physical nonremovable drives require separate host admission. A short-lived, single-use token plus the reviewed identity authorizes the adapter; confirmation rechecks device identity, capacity and image bytes. The adapter must atomically revalidate ownership when opening the destination, support cancellation and return a readback SHA-256, length and device identity. No host disk writer is installed by default, and tests use only an in-memory adapter. Cancellation can leave incomplete media and must not be described as recovery proof.

Verification and remaining acceptance

Run node --test tests/deployment.test.cjs. Fixtures verify traversal rejection, disk partition metadata, manifests/compliance, exact hypervisor and conversion argv, topology/media attachment and preservation, stale previews, concurrent operations, host-configuration drift, partial failures, host-enrolled HTTP requests and readback, typed remote ownership and flash identity/token failures. No physical device is written.

PH07 remains incomplete. Pending evidence includes actual Windows VirtualBox/VMware versions, BIOS and UEFI guest boot/login/network/persistence/graceful shutdown, complete desktop/account provisioning, safe appliance import, native bridged/host-only network acceptance, ISO export, SDK export and consumer smoke build, remote helper/transfer/recovery, scoped credential-vault integration, real provider account/readback runs and platform flashing/cancellation/recovery. Secure Boot has not been tested or claimed.
