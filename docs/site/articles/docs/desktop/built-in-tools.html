Built-in tool services

The main-process entry point is src/main/tools/index.cjs, exporting createToolsService(options). Its asynchronous execute(request, {signal, onProgress}) returns an ok result or a stable error code. The service does not expose a shell, arbitrary URL, renderer file path, environment expansion or PATH executable discovery. Connect it only through the validated application broker. Do not expose host options to the renderer.

Host integration supplies resolveGrant(id, mode), returning an absolute file or directory path from an existing authorized picker grant. Executable records are {path, sha256, bundled: true} under executables. Every invocation rehashes the executable. These records require independent packaged-artifact admission; setting the flag is not package verification. isolationVerified is required for external conversion. This gate must only follow actual sandbox verification. The implementation does not itself establish a portable OS converter sandbox.

Ollama requests always use http://127.0.0.1:11434 and fixed API paths. Responses, request sizes, stream lines and durations are bounded. Pull/chat progress is parsed incrementally, UTF-8 boundaries are retained, error records fail the operation, and AbortSignal cancels transport. There is no invented catalogue or model download success. The managed controller includes a fully inventoried pinned official Windows x64 manifest; unsupported hosts without a reviewed matching manifest remain unavailable. The low-level installer reports MISSING_VERIFIED_PAYLOAD when no manifest is supplied. A supplied pinned payload supports verified cached installation or explicitly enabled bounded official acquisition, strict archive inventory and digest checks, safe extraction and atomic versioned installation. Existing models and installations are untouched.

The converter catalog includes documents/PDF, images, audio, video, archives, structured data/spreadsheets, code/text and binary encodings. Each category has a separate searchable format list and regex workbench. Native UTF-8 text preservation, JSON/CSV table conversion and binary base64/hex encoding perform actual file work. JSON object arrays become CSV tables with a union of column names; CSV rows become JSON arrays. Nested values and spreadsheet formula prefixes are rejected instead of being silently changed. CSV cannot preserve original JSON value types. Text conversion preserves line endings and rejects invalid UTF-8. Native input is limited to 64 MiB; structured operations additionally bound rows, columns, fields and total cells.

converter.inspect reads at most 64 KiB from the selected source to identify known byte signatures or a UTF-8 text sample. The UI reports sample length and file size. This preview is not full decoder validation. The only external converter consumers are native-broker image PNG/JPEG/WebP, audio WAV/MP3/FLAC and video MP4/WebM operations. Generic FFmpeg, ImageMagick, Pandoc, LibreOffice and tar plain-process conversion is not admitted. The catalog keeps available: false for external formats and reports attemptAvailable separately after the branded broker checks packaged integrity. The interface explicitly labels the corresponding action as an isolated attempt and keeps runtime acceptance unverified. The installed executable alone is not runtime evidence.

The host loads resources/native-file-broker/broker-manifest.json and its exact named executable, plus the existing offline payload inventory. It passes native picker grants directly to the branded broker. Only the selected adapter's executable directory is staged from its declared members; the existing payload manager separately validates the complete packaged tool inventory. Missing native broker source, manifest, compiled executable, matching payload inventory or supported platform leaves the attempt unavailable before a decoder starts. No user-selected executable, renderer path or renderer command line enters this route.

Each isolated attempt obtains actual native OS admission before the decoder is resumed. Success requires an operation-bound receipt with zero network capabilities, AppContainer/LPAC and job/handle enforcement, source/output SHA-256, bounded output length, signature plus decoder round-trip validation, and atomic non-replacing publication. These fields describe that operation's output, not blanket runtime acceptance or source equivalence. converter.cancel requests cancellation only for this service's active isolated conversions; queue cancellation retains its per-job scope. A fully validated published result is not relabelled as cancelled merely because cancellation arrived after completion. Failed native attempts retain an opaque temporary-output name only when the broker confirms it; an interrupted or disconnected result is displayed as publication unconfirmed. These outcomes survive queue storage and history export without exposing source paths. A malformed completion receipt is explicitly converted to publication-unconfirmed at the consumer boundary, even when the broker error omitted partial-output metadata; it never implies rollback or deletes a possibly published output. Native converter runtime acceptance remains unverified. The added video consumer has not been built or run in this lane; complete PDF coverage and document/archive isolation consumers remain unavailable. Extract/reorder have the narrow native route described below.

Video attempts use the fixed native operations ffmpeg-mp4 and ffmpeg-webm. MP4 uses libx264 with the veryfast preset and yuv420p, optional first AAC audio, and fragmented streaming flags +frag_keyframe+empty_moov+default_base_moof. WebM uses libvpx-vp9 with realtime/cpu-used 8/row-mt 0 and optional first libopus audio. Both require the first video stream, keep only the optional first audio stream, and omit subtitles, data, global/stream metadata and chapters. These are lossy profiles without deliberate resizing or truncation. The renderer discloses those changes before the explicit isolated attempt, using the shared authored-copy localization boundary. The catalogue does not claim that the packaged FFmpeg build has passed codec/runtime acceptance. Pipe input may not support a source's seeking requirements; decoder, codec or resource-limit failures stay failures, preserve the source and never invoke a plain-process fallback. Output still requires signature, a second constrained forced-demuxer decode, held-handle digests and atomic non-replacing publication.

Outputs are staged beside the destination, bounded, checked for expected signatures where supported, hashed and published without replacing an existing destination. Storage is checked before conversion, and file capabilities are rechecked before publication. The PDF adapter no longer uses a generic process route or an isolation Boolean. pdf.catalog lists inspect, split, merge, extract, reorder, rotate and metadata, with explicit unavailable reasons. Extract, reorder, merge, rotate and metadata removal can become packaged isolated attempts only when the native broker declares the exact operation. They use the packaged qpdf executable directory and its declared DLL members, one original source up to 64 MiB, and 1–1,000 explicit page selections in the range 1–10,000. The native broker further rejects selections outside the inspected input page count. pdf.cancel targets only this service's active isolated PDF operations; the ordinary queue path keeps per-job cancellation.

Native qpdf operates on fixed seekable read-only copies whose hashes match the held original/output handles. The consumer requires all 13 native receipt fields and the two host capability fields, including input/expected/output page counts, bounded bytes, source/output digests, LPAC/job/handle admission and atomic non-replacing publication. The validation class is qpdf-structure-and-page-count. That proves neither independent visual equivalence nor page-order equivalence, and the UI explicitly says so. Encrypted, signed or unsupported-feature documents are not represented as supported merely because their initial bytes begin with a PDF signature. Missing or malformed receipts remain publication-unconfirmed; retained incomplete outputs are not silently deleted. Inspect and multi-output split remain disabled until their own bounded protocol and receipt are implemented.

Merge uses 1–8 original grants in displayed order, at most 64 MiB aggregate original bytes and 10,000 aggregate pages. Its exact 15-field native receipt adds sourceSha256s and inputPageCounts in source order; the consumer requires matching lengths, first digest equality and summed input/expected/output page counts. The interface includes explicit source move controls. Visual and page-order equivalence remain unverified.

Rotate accepts a single source, at most 1,000 distinct selected page numbers, and clockwise 90/180/270 degrees. Its 15-field native receipt adds matching degrees and rotationVerified: true, with validation qpdf-structure-page-count-and-rotation. The native protocol compares effective inherited rotations on every selected and unchanged page. Metadata removal accepts one source and only mode: 'remove'; its 15-field receipt requires metadataMode: 'remove' and metadataAbsent: true, with validation qpdf-structure-page-count-and-metadata. The protocol verifies that trailer /Info and catalog /Metadata are absent, with unchanged page count. This is not full metadata, document-text, embedded-file or active-content sanitization. Every extended receipt additionally has the two host capability fields. All operations preserve uncertain-publication and retained-incomplete outcomes, and none claims visual equivalence. These PDF source changes have not been compiled or executed in this lane.

The native batch picker selects at most 100 source files per page and a user-selected output folder. It derives new names from each complete source basename and the chosen output extension, rejects duplicate names or existing destinations, and returns capabilities rather than paths to the renderer. Select-all, select-none, queue-selected and release-permissions controls operate on the current bounded page. Successfully queued items disappear from the staged batch; a later failure preserves the remaining selection.

The disk queue stores one JSON record per item in host-supplied queueDirectory and admits conversions, PDF operations and model pulls. Processing is serial and reads one record at a time. Server paging retains at most 100 records; the renderer displays 25 records without accumulating previous pages. There is no total queue-length cap. Live native-picker capabilities remain bounded at 512; terminal records release capabilities not referenced by another pending record. Users can process successive batches without a lifetime selection cap. File retry and restart require explicit native-picker reauthorization; no path persisted in a queue record becomes authority. Rebinding is rejected while the queue is consuming.

Pause finishes the current file before stopping, and its control state is stored locally. Start, completion timestamps and per-file outcomes persist; the visible page refreshes while processing without fabricating byte percentages. Recovery marks orphaned running entries interrupted and never silently retries them. Queue history exports as streamed JSON Lines through a new output capability, including operation, state, timestamps and result fields but excluding source paths, grant identifiers, model prompts and document content. The queue requires single application-instance ownership. Crash-atomic control durability across power loss, large real-world queue behavior and packaged/runtime acceptance remain unverified.

The 2026-10-16 source extension intentionally ran no tests, static analysis or runtime/visual checks. Its first root build was cancelled after toolchain acquisition because further source changes superseded that candidate. A later successful build receipt and runtime acceptance must be recorded separately.

Minecraft Java version discovery uses Mojang's official manifest. Downloads follow only allowlisted official HTTPS hosts without redirects, enforce declared size and verify the official server SHA-1 before publishing server.jar. Configuration accepts typed properties, requires online authentication and explicit EULA acceptance, and refuses to overwrite existing configuration. Local Java processes use an admitted runtime. Local containers require an admitted Docker executable and host-supplied immutable minecraftJavaImage digest; their launch drops capabilities, disallows privilege gain, caps CPU/memory and defaults to disabled networking. Explicit network: 'bridge' with a validated port publishes Java TCP only to 127.0.0.1; it does not expose a public firewall port or establish gameplay readiness. Process handles are owned by this service, and stop only signals an owned child. Server readiness, retained process recovery, graceful console administration, container teardown proof, Bedrock payload acquisition, flavour server installation and SSH targets remain incomplete. Fixed official Bedrock release-page discovery, Fabric/Paper metadata and Modrinth plugin metadata/download verification are callable; plugin installation requires explicit code and licence consent. No unsupported target reports success.

Editor handoff launches only a host-admitted editor with one granted file argument. Host editorIds controls the admission list. The response describes process completion, not independent proof that the editor displayed the document. Forge previews bind provider/repository/source to its current SHA-256. Publication requires explicit matching review, unchanged source, a scoped host getCredential callback and a host forgePublish transport that supplies verified readback. No provider transport or credential is supplied by default; preview does not publish. Secrets never enter returned results.

Additional adapter contracts

ollama.chat returns {completed, message: {role: 'assistant', content}, doneReason, metrics} after the terminal record. Progress remains {type: 'chat-token', message: {content}, done, ...} using Ollama fields; pull progress is {type: 'model-pull', status, completed, total, ...}. Callers can render tokens immediately and use the final message for persistence.

pdf.execute accepts operation (inspect, merge, split, extract, reorder, rotate, metadata), sourceId or bounded sourceIds, destinationId, selected integer pages, rotation degrees (90/180/270), or metadata mode: 'remove'. The pinned qpdf executable is mandatory. Before writes, sources undergo signature, qpdf integrity and bounded page-count checks; outputs undergo integrity and exact page-count checks before atomic publication. Split returns one selected-page output per request; the disk queue can schedule individual selections after host integration. Full post-write verification of page content/order, rotation values and metadata removal is still pending; a passing count is not proof of those semantic properties. The executable protocol fixture exercises invocation and page-count refusal, not native qpdf functionality.

Host Ollama install options are ollamaInstallDirectory, ollamaCachedPayload, allowOllamaAcquisition and ollamaPayload. The payload specifies exact version, platform, arch, length, sha256, kind: 'executable' | 'tar' | 'zip', executablePath, and members: [{path, sha256}]; online acquisition additionally needs an official url. Cached bytes are preferred. Tar handling requires an admitted tar executable and rejects traversal, unexpected files and links before extraction. Installation validates all declared members and preserves existing version directories and model stores. It does not change PATH or startup services, request elevation, or claim daemon health. Acquisition permits only reviewed Ollama release URLs and bounded official asset redirects. Payload provenance remains a host review obligation; renderer requests cannot supply manifests, URLs or destinations.

Minecraft discovery actions are minecraft.bedrock.discovery, minecraft.flavours (flavour: 'paper' | 'fabric', optional Paper version), minecraft.plugins (projectId) and minecraft.plugin.install (versionId, granted directoryId, acceptPluginCode: true, acceptLicense: true). Modrinth plugin downloads require a supported server loader, a primary JAR, fixed CDN origin, exact byte length and SHA-512 match. These controls verify provenance/integrity, not plugin safety. Official Bedrock page changes and unsupported metadata fail visibly rather than fabricating releases.

Native executable admission

createPayloadManager({directory, bundledManifest, dialog, parentWindow}) in src/main/tools/payload-manager.cjs provides host-only list(), choose(toolId) and resolve(toolId). Pass the manager as payloadManager to createToolsService. The manager admits only FFmpeg, ImageMagick, Pandoc, LibreOffice, ebook-convert, qpdf, Java, Docker, tar and Ollama. Renderer requests may provide a known tool ID; executable paths come only from the native file picker. A Cancel-default native notice identifies the selected file, hash and account-permission implications before a fixed bounded version probe runs. A matching basename/version identifies the expected program family; it does not establish publisher authenticity or sandbox safety.

Bundled manifest records take precedence. Changed or invalid bundled bytes fail closed. Explicit user-selected tools retain origin: 'user-selected' and bundled: false; they are never described as packaged dependencies. Selection receipts persist atomically in the private application directory. Each resolution validates canonical path, regular file and SHA-256 again. Version mismatch, cancellation, changed paths and hashes preserve previous admission records. Static renderer-shaped admission records cannot enable the runtime. No PATH search, arbitrary executable ID, network install or automatic execution task is exposed by this manager.

User-admitted native tools provide an explicit local fallback with user consent. They do not satisfy the full bundled offline-adapter requirement or establish converter isolation. The existing converter isolation gate remains required, and unsupported adapters remain disabled. Runtime executable pinning cannot eliminate all same-account filesystem races or prove native runtime success. node --test tests/payload-manager.test.cjs tests/tools.test.cjs covers actual fixture probes, persistence, cancellation, failed-version preservation and changed paths/hashes. These fixtures are not Windows package, publisher, real adapter or graphical runtime proof.

Request admission and owned shutdown

Every tool action has an exact request schema checked before file resolution, network access or process launch. Unknown action names, extra top-level/nested fields, malformed grant IDs, invalid ports and page selections, recursive queue jobs and unsupported value types fail closed. Admitted requests are cloned before asynchronous work. Queue jobs now include typed pdf.execute alongside conversions and model pulls. Persisted records are bounded, reject symlinks and are admitted again before replay; this does not authorize a new file grant after application restart.

createToolsService also returns asynchronous dispose(). Shutdown rejects new work, aborts active operations, waits for owned queue cancellation to persist and stops owned server processes. Containers receive generated application-owned names and fixed Docker stop commands through a freshly revalidated executable. Local children receive termination, then a bounded kill/wait if necessary. Unverified container/process shutdown rejects with PROCESS_STOP_UNVERIFIED; a timer or signal alone is not reported as confirmed cleanup. No unrelated process, container, queue or server is adopted or stopped.

Minecraft start requires a write-capable directory grant because servers write worlds/configuration, plus host-only authorizeServerExecution(directoryId) returning true. The host must tie that callback to explicit native consent to execute server/plugin code from that directory. A renderer field cannot grant this authority. Existing grant consent does not establish safety of a user-supplied JAR. Converter/PDF isolation still requires a real sandbox receipt; native executable admission alone never sets isolationVerified.

Focused fixtures additionally prove rejection before effects, queued PDF adapter protocol replay, streamed transport cancellation with persisted queue state and owned child exit. They do not establish Minecraft gameplay, Docker lifecycle, native qpdf semantics or Windows runtime acceptance.

Pinned managed Ollama installation and recovery

The managed controller is createManagedOllamaController in src/main/tools/ollama-managed.cjs. Host options include a private absolute directory, native dialog/parentWindow, optional verified bundledPayload and optional reviewed manifest. Passing ollamaManagedDirectory through the tool options constructs it automatically. On Windows x64, the default manifest pins official Ollama 0.40.5, published on 2026-10-14. Other managed platforms remain unavailable unless the host supplies a separately reviewed matching manifest.

Request Behavior
ollama.managed.status Report manifest availability, installed-byte validation, phase, version and owned process state.
ollama.install with optional Boolean acquire and repair Show native installation review; use verified bundled/cache bytes first, optionally acquire the pinned official payload, and install without starting.
ollama.managed.start Explicitly start admitted files with private model storage and verify exact owned listener/version; unavailable without the required native ownership callbacks.
ollama.managed.stop Stop only the retained owned process tree and require settlement proof.

The controller owns separate versions, cache and models subdirectories and an atomic installation receipt. It preserves existing system/user Ollama installations, model stores, configuration, PATH and startup settings. Installation never silently starts a runtime. Corrupted owned versions require explicit repair: true; repair retains the old directory, promotes the fully verified new directory and restores the prior directory if promotion fails. It does not delete existing models. Progress reports type: 'ollama-install' and phases download, extract, verify, promote and installed, with byte totals where known. Callers pass an AbortSignal; the host controller also exposes cancel() and dispose().

The official archive was downloaded into ignored development cache and inspected on Linux without installing or executing Windows software. Its exact size is 1,471,226,485 bytes and its SHA-256 is 5134ce7e3bc8e94d0494721c799ec293b429450d0c52461b0ee3647dd3bb4bb7, matching the official GitHub release API digest. All 82 regular members, totaling 1,942,972,275 expanded bytes, were independently read and hashed. The committed manifest contains every member name, length and SHA-256. The original archive and extracted third-party payload are not committed. The tagged upstream MIT licence is retained as src/main/tools/ollama-LICENSE.txt; the official archive contains 16 additional licence/notice files, retained unchanged during extraction.

Native Node ZIP handling validates the central/local member identities, complete inventory, expansion bounds, expected hashes, duplicate/case-colliding names, unsupported encryption/compression and unsafe Windows path aliases before atomic publication. It does not invoke an installer executable, shell, external unzip utility or unpinned download. Transfers admit only the pinned official release route and reviewed official asset redirects. Storage is checked before staging; cache bytes and extracted files are verified again. No Windows execution is performed by the Linux fixtures.

Publisher evidence has explicit limits. The archive came from the official Ollama GitHub release and matched its published digest. The PE header identifies AMD64, and its embedded PKCS7 certificate subject names Ollama Inc. Windows Authenticode image verification, trust/revocation validation, final-handle identity/sharing protections, native install/button behavior and long-path/runtime acceptance remain unverified. Inspecting embedded certificates is not signature verification. Managed startup uses the built-in Windows ownership adapter or explicit host verifyListener({pid, host, port}) and stopOwnedTree({pid, child}) callbacks returning matching verified/settled PID evidence. Platforms without those native capabilities return OWNED_RUNTIME_VERIFICATION_UNAVAILABLE; an existing unrelated loopback listener is never adopted. Native execution, descendant settlement and GUI proof remain separate from verified payload acquisition/extraction.

Run node --test tests/ollama-managed.test.cjs tests/tools.test.cjs tests/payload-manager.test.cjs. Fixtures prove actual ZIP extraction, hash/inventory refusal, private cached installation, explicit acquisition, confirmation cancellation, corruption recovery and preservation. They do not establish Windows runtime acceptance or complete the full Ollama-suite roadmap requirement.

Cancellation evidence distinguishes native review cancellation, cancellation during a real streamed HTTP download, and cancellation during actual ZIP extraction. Download/extraction fixtures verify that incomplete installed files are removed, verified cache remains reusable after extraction cancellation, and installed/model preservation tests retain prior bytes. Windows cancellation and GUI interaction are still deferred.

Windows managed runtime ownership adapter

Windows hosts now construct createWindowsOllamaProcessAdapter automatically for managed Ollama. The adapter uses a fixed application-owned PowerShell/C# helper through the host system PowerShell executable, with no profiles, shell expansion, execution-policy change, renderer executable or renderer command string. All launch data travels as typed JSON over private pipes. Other platforms still require a separately supported ownership adapter; Linux fixtures never run the Windows helper.

The helper opens and retains the admitted executable/library files with read-only sharing, checks their exact length/SHA-256, final path, reparse status and hard-link count, and protects their directories. It creates Ollama suspended, assigns it to a new Job Object configured to terminate on handle closure, captures retained process handle/PID/creation-time/executable identity, then resumes execution. Failure to assign the job prevents normal execution. The runtime receives fixed serve arguments, a loopback-only host and the application-owned model destination. Long-path prefixes preserve the same native handle checks.

Before health/version acceptance, the helper verifies the retained root process is alive and Get-NetTCPConnection attributes the loopback 11434 listener to that exact process. Protocol replies bind a private nonce, request ID, PID and creation time. Mismatched images, reused PIDs, unexpected responses, unavailable native modules and missing ownership evidence fail closed. Status refresh checks actual owned listener/version; while an installation/start operation is active, it reports the current phase and retained installation verdict without repeatedly hashing approximately 2 GB of files.

Stop targets the retained Job Object, waits for its active-process count to become zero, then releases native file protections and closes the helper. Concurrent stops share the same operation. Cancellation during launch closes the control pipe; the helper checks for cancellation before execution and terminates/settles any already-created job before reporting cleanup. Helper crashes or missing settlement proof produce an unverified-stop error rather than a successful stop. Application disposal also accounts for launches still pending identity establishment. Unrelated existing services/listeners are never adopted, signalled or terminated.

ollama.managed.cancel is a strict no-argument action returning {cancelling: boolean}. It cancels an active installation/start operation while its original request remains pending; stopping an established runtime remains the distinct managed stop action. Progress/status remain available during a download. The Linux protocol fixtures cover correct handoff, PID/image mismatches, failed settlement/retry, concurrent stop, cancellation and disposal races. They validate the JavaScript protocol boundary only. The PowerShell/C# source has not been executed on Windows: native compilation, policy/module availability, Job Object behavior, listener attribution, long-path/file-sharing behavior, startup/stop/cancellation and GUI acceptance remain explicitly deferred.

Evidence-based model planning

Three typed local operations are available: ollama.hardware, ollama.fit (model, optional contextTokens from 128 to 1,048,576), and ollama.capabilities (model). The selected model must exactly match an installed tag or digest returned by the real local API. The adapter reads bounded /api/tags, /api/show, then /api/tags again and rejects observed digest/size changes. Ollama provides no atomic tags/show transaction; this consistency guard is not an immutable server-side snapshot. No remote catalogue, model-name inference or invented hardware record is used.

Hardware reports actual host total and currently available physical RAM separately, CPU architecture/core count, and free/total space on the host-supplied model destination volume. Private paths are omitted from results. GPU and CPU-backend support remain unknown unless the host supplies ollamaHardwareProbe({signal}). That callback can return {cpuBackendSupported: boolean, gpu: {state: 'verified', observedAt, devices: [{backend, driverSupported, totalBytes, availableBytes}]}}. Supported backend identifiers are CUDA, ROCm, Vulkan and Metal in lowercase. Malformed, failed or older-than-five-minute probe data stays unknown. The default implementation does not claim a native GPU/driver probe exists.

Fit results carry a timestamp, the model digest/declared metadata, hardware evidence, reasons, assumptions and one of Runs well, Runs with limits, Unlikely or Unknown. Weight size comes from the actual installed artifact inventory. For supported standard-attention architectures, declared layer/head/embedding or key/value widths determine an explicitly disclosed f16 KV-cache estimate. A default planning context is at most 4,096 tokens and never exceeds the declared model maximum. The estimate reserves runtime overhead plus a 20% margin. Unsupported/missing metadata returns Unknown. Quantization/model names never substitute for actual size or missing dimensions.

Runs well requires verified compatible single-device available GPU memory and current available RAM to cover the estimate. Runs with limits requires verified CPU support/current RAM fit and makes no GPU-offload claim. Unlikely requires insufficient current memory under the available verified placement evidence; total RAM is never treated as free RAM. Potential hybrid placement without verified allocation remains Unknown. Without GPU evidence, the overall verdict remains Unknown even when the separately displayed RAM estimate fits. These are conservative text-only memory planning results, not throughput promises, attachment-memory estimates or successful model-load proof.

Capabilities come only from /api/show declarations and retain unknown values when declarations are absent/malformed. Image capability and tool calling do not imply an attachment transport exists: attachments.transferEnabled remains false with an explicit missing validated-transport reason. Official exhaustive revisioned catalogue refresh, full tag pagination/offline cache, native GPU probing, attachment decoding/upload and harness checkpoint/rollback remain incomplete. Focused model-fit fixtures are synthetic protocol/evidence records; the hardware/disk fixture reads actual Linux host metrics and does not prove Windows/GPU runtime behavior.

Model, fit and capability responses explicitly qualify identity as identityConsistency: 'matching-tag-before-and-after'. The show request uses the mutable selected tag, including when selection originally used a digest. Matching digest/size before and after detects observed net changes but cannot prove atomic metadata, an unchanged tag throughout the request (the ABA case), or an immutable digest-bound show receipt. Returned limitations state this directly. This implementation does not assume that the official show API accepts immutable digest addressing. Standalone metadata extraction without the before/after guard is labelled unverified-tag-show-association.

Official observed model catalogue

createOllamaCatalogue({directory, fetchImpl}) in src/main/tools/ollama-catalogue.cjs refreshes and caches the public official Ollama library. The desktop host supplies a private ollama-catalogue directory through ollamaCatalogueDirectory and admits its four typed actions through the existing tools boundary. Other trusted consumers may inject an existing controller as ollamaCatalogue. Requests are ollama.catalogue.status, ollama.catalogue.refresh, ollama.catalogue.cancel, and ollama.catalogue.page with optional family, plain-text query, zero-based offset and limit (1–100). No renderer URL, headers, credentials, cookies or source override is accepted.

The Local assistant workspace now exposes catalogue status, official refresh and independent cancellation, cached model-name search, 50-item paging and family drill-down. Its adjacent regex builder filters only the loaded page through a bounded worker. Status distinguishes observed counts, last successful refresh, last attempt and staleness. Missing exact metadata remains Unknown; catalogue browsing never installs or starts a model. Late cancellation reports publication in progress and requires final status readback. These controls use the actual typed host actions; browser fixtures verify presentation and request behavior, separately from the historical live traversal below.

The adapter reads https://ollama.com/library?sort=alphabetical, discovers every admitted family link, then traverses each official /library/{family}/tags source and observed supported pagination. A bounded tokenizer supports quoted and unquoted attributes, keeps quoted attribute contents separate from real attributes, and excludes raw-text/template/comment contents from links and metadata. Unterminated tags, comments and raw-text elements fail closed. Parsing extracts data only; scripts, styles, comments and external instructions are never executed. Requests are fixed to the official HTTPS origin and exact library/tag-list path patterns. Pagination keys/values are admitted narrowly; external/unsupported pagination, dynamic infinite-scroll shapes, changed titles, empty or truncated pages fail closed. Redirects are disabled, authentication/cookies are omitted, response type/UTF-8 is checked, and opaque source strings never become commands or inferred capabilities.

A refresh uses two workers, a 125 ms per-request pause, a 20-second per-request timeout and a ten-minute overall deadline. Global limits are 10,000 pages, 256 MiB response bytes, 8 MiB per response, 5,000 families and 100,000 variants. Reaching any limit makes that attempt incomplete and preserves the previous valid cache. Cancellation aborts active fetches and settles both workers. A complete observed traversal is staged, hashed, synced and atomically promoted. Accepted cancellation before publication preserves the last successful snapshot. Immediately before atomic rename, publication enters a noncancellable refreshPhase: 'publishing'; a cancel request then returns {cancelling: false, reason: 'CATALOGUE_COMMIT_IN_PROGRESS'}. This distinguishes a rejected late cancellation from an accepted abort. Cache admission reads through one retained nofollow file handle in bounded chunks up to its initial length plus one byte, with a 64 MiB maximum. It checks regular-file/link status and pre/open/post/path/root identity, size and change timestamps; growth, replacement and symlink races fail closed. It then rechecks record hash, provenance origins, schema and bounds. Cached reads require no network. Page/status responses include the retained revision/time, age/staleness, source availability at the last attempt and partial refresh progress. Staleness defaults to 24 hours; a recent observation is not proof that upstream has remained unchanged.

The revision is a SHA-256 of the retained local snapshot, not an upstream release revision. Each source records its URL, response SHA-256, observed time, byte count and available ETag/Last-Modified headers. The snapshot records refresh start/completion times. completeness.traversal is complete-observed-official-source, while exhaustive and metadataComplete remain false: the upstream HTML has no authoritative total or atomic revision that proves an exhaustive, simultaneous inventory. Models/tags changing during traversal, unannounced source structure and historical/deleted entries remain outside that proof. No curated or hardcoded list substitutes for the source traversal.

Tag rows retain exact selected tags and normalized source display labels for approximate size, context, input type and visibly marked short digest. Display sizes/context stay opaque strings; sizeBytes, contextTokens, capabilities, quantization and license are null where exact admitted metadata is absent. Neither model names nor input labels establish runtime capabilities, licence rights or loading/performance recommendations. All remote fit verdicts remain Unknown. The existing installed-model fit/capability operations remain separate. Optional registry-manifest/config/licence admission and richer exact metadata are not implemented by this unit; no model blobs are downloaded.
