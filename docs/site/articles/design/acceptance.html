Design and runtime acceptance plan

Status: all production evidence unverified. Design-review approval is separate from implementation and runtime acceptance.

Presentation matrix

Proposed normal client area 1440×960, proposed minimum 960×640; English/Cantonese/bilingual; light/dark; 100/125/150/200% scale. This is 48 tuples for each inventoried screen/state before additional special states. Website viewports cover approximately 320 pixels upward separately.

Bind every result to exact source commit, build receipt, packaged artifact hash, screen/state, language/theme/viewport/scale, capture method and privacy verdict. Capture every inventoried normal-size state and the full required matrix. Measure target/ancestor geometry and winning computed layout values. Correct and rerun the identical tuple after a fix.

Real Windows application input, installation, updates and guest boot proof require their actual supported runtime. Cloud/Linux browser automation can inspect appropriate built surfaces without touching a visible desktop; it never substitutes for native Windows or installer proof. Preview fixtures remain labelled fixtures.

Functional evidence

  • Typed Kconfig semantics and immediate requested/effective reconciliation, undo order and failed-write rollback.
  • WSL/Docker prerequisites, path compatibility, task ownership, concurrent output locks, cancellation and interrupted recovery.
  • Buildroot plus supported kernel/BusyBox/U-Boot configuration; real custom package/overlay/external-tree round trips.
  • Genuine ISO/VMDK/VDI/OVA structures and VMware/VirtualBox import/boot/runtime captures for claimed compatibility.
  • Rich controls and canvas consumers; failure when substituted by generic textbox forms or misleading viewers.
  • Per-surface shared feature completeness, offline packaged adapters, every regex instance, persistence, localization and accessibility.
  • Browser pairing, typed capability boundaries, revocation, origin/CSRF/replay/transport restrictions and actual browser behavior.
  • Fresh-host bootstrap, full bundled capabilities, Squirrel install/update/rollback and prior-state preservation.
  • Current public website routes/articles/wiki/assets/downloads/About homepage and release source/asset readback.

Negative completeness guard

Use a hand-written required feature identity list. For every claimed delivered feature, remove or disable an implementation, registration, article, localized string, focused test, interaction receipt or capture and require failure. Restore it and require success. Exact identifiers/boundaries prevent a partial substring or sibling surface from keeping the guard green.

Keep source, implementation, packaged offline capability, native runtime, GUI and public delivery as separate states. Do not tick a roadmap item or claim release completeness from design references or catalogue presence.
