# Configuration service

The main-process configuration service reads the output `.config`, retaining unrecognized lines during typed edits. Symbol names and bool, tristate, string, integer and hexadecimal values are validated before writing. Its injected workspace resolver must return explicitly granted canonical source and separate output roots. Its executor must perform the admitted real `olddefconfig` operation and report success; there is no simulated make fallback.

`createConfigurationService({resolveWorkspace, executor})` exposes `inspect`, `apply`, `listDefconfigs`, `applyDefconfig` and `undo`. Requests identify `workspaceId`; changes additionally require the SHA-256 `revision` returned by inspection. Each output root has an in-process serial queue. Writes use a same-directory temporary file and rename; failed reconciliation restores the prior configuration. Twenty prior configurations support ordered undo. Successful reconciliation returns effective values and differences from requested values. Defconfig discovery is bounded to regular files in the granted source `configs` directory and rejects directory or file symlink escape.

The offline Kconfig adapter vendors upstream Kconfiglib 14.1.0 under its ISC license. `scripts/configuration/vendor/provenance.json` records the official PyPI metadata URL, archive URL, verified archive SHA-256 and vendored file hashes. No runtime download is required. `createKconfigAdapter({pythonExecutable, admitted:true})` requires an absolute host-admitted Python executable and supplies the optional `semanticAdapter` constructor argument. It returns the actual menu tree, symbol types and values, choices and selection, ranges, defaults, dependencies, visibility, assignable states and help. Typed edits against an available adapter reject undefined symbols and mismatched types.

The host resolver can provide `kconfig: {entrypoint, prefix, environment, externalRoots}` alongside each granted root pair. Buildroot normally uses `Config.in` and an empty prefix; Linux-style domains use `Kconfig` and `CONFIG_`. These settings come exclusively from the trusted host resolver. The helper receives a controlled environment, rejects file reads outside explicitly admitted source/output/external trees, blocks subprocess evaluation and Python plugin execution, limits depth/node count/JSON output and runs with a timeout. Kconfig configurations requiring command expansion therefore fail truthfully until a separately admitted evaluation path is available.

Kernel, BusyBox and U-Boot domains use explicitly discovered host root pairs under resolver `domains.linux`, `domains.busybox` and `domains.uboot`. Each must independently carry `granted:true`; no package output path is guessed. Each may supply an allowlisted `reconcileTarget` such as `olddefconfig`, `linux-olddefconfig`, `busybox-oldconfig` or `uboot-olddefconfig`; the executor remains responsible for performing the actual admitted operation against the intended Buildroot or component tree. Missing domain grants are rejected. Semantic adapter readback does not establish compatibility with a particular Buildroot version's generated environment. Actual Buildroot make acceptance remains distinct and pending.

Source defconfig minimal saving, ordered external defconfig discovery and persistent cross-process locks remain pending. In-process serialization does not protect against external tools editing the same output concurrently.

The package model validates build system, source, hashes, license, ordered patches and overlay mappings with permission modes. `savePackageModel` atomically saves a revision-checked JSON model under an explicitly granted root. This JSON storage API is separate from the external-tree recipe authoring API below.

Focused verification: `node --test tests/configuration*.test.cjs` exercises actual local Python Kconfig types, menus, choices, ranges, dependency/help and loaded values, typed validation, actual isolated Node helper reconciliation and failure, rollback, undo, racing revisions and symlink rejection. This establishes the service contract, not Buildroot make acceptance, Windows, WSL or Docker runtime acceptance.

## External package authoring

`createPackageAuthoringService({resolveExternalTree, withLock})` in `package-authoring.cjs` provides `preview` and `apply`. The host resolver receives only workspace and external-tree identifiers and supplies an explicitly granted root. The host lock remains held across each complete asynchronous operation and must exclude configuration, build and source mutations against that tree. Renderer requests cannot supply a filesystem root or shell command.

A prepared external tree must already contain regular UTF-8 `external.desc`, `Config.in` and `external.mk` files. The descriptor supplies the validated external name. Preview generates `package/<name>/Config.in`, `<name>.mk` and `<name>.hash`, and shows exact before/after text for these files and external integration lines. Existing root content is retained; standard documented wildcard make inclusion is recognized to avoid duplicate recipe evaluation. Existing generated-path files are overwritten only by applying the exact reviewed revision and preview hash. Other package files are untouched.

The typed model requires name, version, HTTP(S) source archive URL, source filename, homepage, license expression, license filenames, build system, build dependencies, explicit Kconfig dependency symbols, help and SHA-256/SHA-512 hashes. Every source archive and license filename requires a hash entry. Hash values are declarations supplied for review; this operation does not fetch upstream content or establish their correctness. Literal values reject Make/Kconfig injection and path traversal. Python packages require a supported explicit setup type. Generic package recipes contain metadata only and display a warning that custom build/install commands require a separate reviewed workflow. Patch content, overlay copying, hooks, dependency inference and custom command authoring are not implemented by this API.

Apply rechecks all before-images and the generated preview under the host lock, then writes same-directory temporary files with retained permissions and renames. It snapshots affected text and modes in memory and restores written files, removes newly created files and removes newly created empty directories after a write failure. A restoration failure reports `PACKAGE_ROLLBACK_FAILED` rather than claiming success. A process crash is not covered by this in-memory rollback; no crash recovery claim is made. Symlink files and directories, oversized files and non-UTF-8 existing content fail before modification.

Recipe formatting follows the upstream Buildroot manual's [package directory](https://github.com/buildroot/buildroot/blob/2025.02.1/docs/manual/adding-packages-directory.adoc), [generic infrastructure](https://github.com/buildroot/buildroot/blob/2025.02.1/docs/manual/adding-packages-generic.adoc), and [external tree](https://github.com/buildroot/buildroot/blob/2025.02.1/docs/manual/customize-outside-br.adoc) contracts. Focused tests execute actual temporary-tree preview/apply, negative injection and symlink checks, stale-preview rejection and injected partial-write rollback. These checks do not establish runtime package build acceptance.

## Initialize an external tree

The package authoring service also exposes `previewInitialize` and `applyInitialize`. Both take `{workspaceId, externalTreeId, descriptor: {name, description}}`; apply additionally requires the preview's `revision` and `previewHash`. The directory comes from the same host resolver and remains protected by the same asynchronous host lock. It must already exist and be completely empty. Existing prepared, partial or conflicting trees fail with `EXTERNAL_DIRECTORY_NOT_EMPTY` and remain untouched.

Names contain 1–64 ASCII letters, digits or underscores and start with a letter. Descriptions contain 1–80 ASCII letters, digits, spaces or basic punctuation (`. , _ ( ) + -`) and start with a letter or digit. Extra descriptor fields and multiline or executable interpolation content are rejected. Preview displays exact contents for `external.desc`, `Config.in` and `external.mk`; the last file uses Buildroot's documented sorted package wildcard include. Its revision binds the canonical selected directory, filesystem identity and empty state. The preview hash also binds all generated content, so changing the descriptor requires a new review.

Apply creates each file through an exclusive same-directory temporary file and atomic no-overwrite hard-link publication. It does not replace files that appear after preview. A partial failure removes only files published by the transaction, after checking their current contents still match; unrelated concurrent files remain. Changed transaction files or failed restoration produce `PACKAGE_ROLLBACK_FAILED`, preserving the conflicting content. Initialization is an in-memory transaction and does not claim crash recovery. The initialized tree can immediately use the existing package recipe preview/apply API. Linux filesystem fixtures verify actual initialization, revision/identity changes, conflicts, descriptor injection and injected partial-write preservation; native Windows and actual Buildroot execution remain unverified.

## Activated external Kconfig inputs

For Buildroot inspection, the trusted host resolver supplies `kconfig: {buildroot: true, externalRoots: [canonicalRoot, ...], environment: {HOSTARCH, HOST_GCC_VERSION, BR2_VERSION_FULL}}`. External root order is retained. Each external tree must contain regular non-symlink `external.desc` and `Config.in` files; descriptor names must be unique. Names and descriptions are read from the actual granted descriptor rather than accepted as renderer environment variables. The adapter derives each `BR2_EXTERNAL_<NAME>_PATH` and `_DESC` value and returns the ordered descriptor summaries in `semantics.externalTrees`.

The bridge derives source/output/configuration environment paths and supplies the generated `.br2-external.in.paths`, menus and supported provider inputs as read-only in-memory files. These inputs include the actual external `Config.in`, nested package definitions and existing `provides/{toolchains,jpeg,openssl,skeleton,init}.in` or `linux/Config.ext.in` files in their selected order. This follows the source tree's generated external-input structure without modifying its output directory or running its shell script. Nested include symlink escapes remain blocked by the read boundary. External-version discovery and equivalence across all Buildroot releases are not established by this adapter.

A read-only inspection was executed against the actual [Buildroot 2025.02.1 release archive](https://buildroot.org/downloads/buildroot-2025.02.1.tar.xz), downloaded to a temporary directory (observed archive SHA-256 `a3216907e7ce1bbd38413e20b0861641b160ecc40dd7b598febb7f12984b3206`). It parsed 11,467 menu nodes without external trees, retaining eight library warnings, and the real-source fixture also loaded a granted external package. This is inspection evidence for that source version, not actual `make olddefconfig`, build, Windows or supported-version certification. Reproduce the optional fixture with `MATERIAL_BUILDROOT_KCONFIG_SOURCE=/path/to/buildroot-2025.02.1 node --test tests/configuration-external-kconfig.test.cjs`; ordinary fixtures independently test ordering, effective loaded values, providers, duplicate descriptors, symlink rejection and an unchanged output directory.

## Discover and import existing packages

`createPackageDiscoveryService({resolveRoots, withLock})` reads host-authorized source and active external trees. `resolveRoots(workspaceId)` returns `{granted:true, sourceRoot, externalTrees:[{id,root}]}`; `withLock(canonicalRootsArray, asyncWork)` protects the whole read. Requests contain identifiers and search controls, never filesystem paths. The module executes no source, shell, Make or Kconfig code.

`discover({workspaceId, query?, offset?, limit?})` scans actual package directories and returns deterministic package identities, recipe hashes and static Kconfig declarations with types, prompts and source-relative locations. `Config.in.host` and recipes without a Kconfig declaration remain discoverable. Search is a plain case-insensitive substring across actual names, paths and declarations. This static source catalogue is separate from evaluated Kconfig menus, visibility and effective dependencies.

Pages default to 50 entries and allow at most 100. `nextOffset` advances by the returned entry count because the 512 KiB page-content budget may shorten a page. Responses include total matches, revision, explicit scan limits and symlink-skip warnings. Each scan permits at most 50,000 directory entries, 64 MiB of recipe/configuration bytes, eight directory levels and 15 seconds. Per-file discovery reads stop at 1 MiB. Package declaration summaries and help details have separate count and byte limits with truncation indicators.

`importPackage({workspaceId, packageId, revision})` checks the catalogue revision, then reads the discovered package as a bounded snapshot. It returns exact available file bytes in Base64, SHA-256 receipts, sizes, literal declaration help and a typed draft where the supported metadata can be safely understood. Only literal supported recipe fields and infrastructure are interpreted; commands, extra variables and other syntax are never evaluated. A missing typed draft does not remove or rewrite the source content.

A typed round trip is allowed only when all recipe/configuration/hash text exactly matches generation from the imported draft and no additional package files exist. Comments, custom commands, extra files, unsupported constructs or unavailable byte content block round-trip replacement. The external-tree authoring service enforces this preservation rule independently and returns `PACKAGE_MANUAL_EDIT_REQUIRED` rather than overwriting an unsupported existing package. A useful draft may still be returned alongside a blocked round trip for review.

Import includes at most 256 files and 32 MiB of inspected package data. Individual byte payloads stop at 64 KiB and total captured bytes stop at 256 KiB; larger files return size/hash metadata and a reason that bytes are unavailable. Hashing stops at 8 MiB per file; larger files explicitly return no hash. Symlink content is never followed. No file is modified by discovery or import.

Filesystem fixtures verify source/external search, pagination, host-only packages, symbol locations/help, exact supported imports, comment/custom-recipe preservation, stale revisions, symlink boundaries and payload limits. An optional test against the downloaded Buildroot 2025.02.1 source discovered more than 3,000 real recipe identities, found BusyBox declarations and preserved the unsupported upstream zlib recipe. Run it with `MATERIAL_BUILDROOT_KCONFIG_SOURCE=/path/to/buildroot-2025.02.1 node --test tests/configuration-package-discovery.test.cjs`. This is source inspection evidence, not actual package build or native Windows acceptance.

Discovery requires the resolver's root paths to already be canonical and rejects a path that now resolves through a replacement symlink. Each service instance retains the first observed device/inode/birth identity for each workspace/tree/root. Host-supplied `sourceIdentity: {dev,ino}` and external-tree `identity: {dev,ino}` can additionally bind the initial call to native-selection evidence. A deliberately reauthorized replacement at the same path needs a fresh service instance. Roots are checked again while holding the host lock before and after work.

Bounded file reads open the leaf with `O_NOFOLLOW` where available, compare open-handle metadata before and after reading, and revalidate canonical directory/file snapshots before returning. Directory listings and the completed catalogue/snapshot similarly recheck their evidence. Observable external replacement or modification fails closed; these checks supplement the in-app lock rather than treating that lock as protection against other filesystem writers. The implementation does not claim an operating-system filesystem snapshot or native Windows race acceptance.

Files with a link count other than one are rejected during path inspection, open-handle checks and final revalidation. Discovery and import therefore do not expose bytes from a file hardlinked into a granted tree from another location. The authoring before-image reader uses the same bounded file-handle checks.

Catalogue revisions stream hashes of configuration and recipe receipts; shared configuration text and symbol arrays are never serialized once per recipe. Retained declarations are bounded to 512 entries/128 KiB per configuration, 10,000 entries/4 MiB per source tree, and 20,000 entries/8 MiB across the scan. Each prompt and help field also has a length cap. `symbolStats` reports retained/declared counts, retained bytes, truncation, configured budgets and streaming revision-input bytes. Truncated declaration text is marked explicitly; search covers all package names and retained declaration text. Changes anywhere in a configuration file still invalidate its receipt even when the changed declaration was omitted from retained detail. Search checks each shared declaration array once rather than constructing repeated aggregate JSON strings.

The authoring preservation check binds each snapshot's hash, mode and file identity to the exact original before-image used by the reviewed revision. Before-images are revalidated before returning preview and each target is checked again immediately before publication. Rollback restores a published file only when its current text and captured published identity still match this transaction. Independent changes are preserved and reported as `PACKAGE_ROLLBACK_FAILED`. These are checks for observable changes, not an atomic filesystem snapshot or a guarantee against every external race.

Publication rechecks the expected file receipt after temporary-file preparation and permission changes, immediately before rename. The same check runs after preparing rollback restoration bytes. New files use exclusive hard-link publication and remove the temporary link before validating their single-link receipt. A target that appears independently is never replaced by this new-file path. The remaining check-to-publish interval is not an operating-system compare-and-swap guarantee.

Authoring also requires the resolver's original root to equal its canonical path, accepts optional native-selection `identity: {dev,ino}` evidence, retains the first observed root identity and verifies it before and after the locked operation. A replaced or redirected selected directory requires fresh host authorization and a new service instance. Fixtures cover edits during temporary preparation in both forward publication and rollback, and rejection of a redirected selected root.
