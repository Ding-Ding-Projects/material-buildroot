# Desktop updates

The main-process update service pins `Ding-Ding-Projects/material-buildroot`. It reads up to ten pages of normal GitHub releases, rejects duplicate tags, excludes drafts and prereleases, and selects supported version/build tags in version and publication-date order. A version older than the installed version is never offered. A same-version build requires a known installed source; encountering that installed source stops discovery rather than offering an older build.

`createUpdateService({userData, currentVersion, currentSource, onInstallRequested})` exposes `check()`, `download()`, `cancel()`, `getState()` and `requestInstall({confirmUnsigned:true})`. The host can poll `getState()` for byte progress. Checks and downloads are asynchronous and cancellable, with one operation at a time. Errors are observable and partial downloads remain available for a later retry. Each network request has a two-minute timeout. A host can schedule discovery after startup; the service itself does not introduce a timer or execute an installer.

The release must contain `Setup.exe`, `provenance.json` and `SHA256SUMS.txt` generated by the existing release preparation script. Asset URLs must name the pinned repository and selected tag. The provenance checksum, schema, version, Windows x64/Squirrel format, unsigned status, installer size/hash and tag commit/source must agree before download. Redirects use HTTPS and a bounded GitHub asset-host allowlist. Metadata is bounded; installers are capped at 2 GiB. GitHub HTTPS and repository control remain the trust boundary: an unsigned checksum manifest is integrity metadata, not an independently signed authenticity proof.

Downloads stream into `userData/updates/<sha256>-Setup.exe.partial`. Interrupted transfers resume only with an exact matching HTTP range response; a full response safely restarts the transfer. Final size and SHA-256 must match before the completed file is linked into place. Existing completed files are verified and reused; existing unrelated user data is untouched. Unsafe directory/partial symlinks are rejected. This is not a defense against an attacker who already controls the running user's account and can race filesystem operations.

The ready state is explicitly `unsigned-ready`. Nothing installs automatically. An explicit unsigned confirmation and a host callback are required, and the installer is verified again immediately before that callback. The callback receives the path, version, source and tag. The host owns unsaved-work handling and any actual installer launch. No restart, shutdown, Squirrel `Update.exe` invocation, silent install or automatic recovery install is performed by this service. Existing `electron-squirrel-startup` remains lifecycle-event handling only; it is not installation consent.

Windows installer transitions, genuine Squirrel upgrade/rollback, native cancellation, unsaved-state preservation, uninstall and physical-host acceptance remain deferred. Linux HTTP fixtures prove network and file behavior only.
