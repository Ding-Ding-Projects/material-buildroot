# Native Docker firmware workspace

The execution backend supports a distinct native-volume workspace for the pinned Buildroot 2025.02 x86-64 BIOS profile. This is not a host-directory project descriptor. Native source, output and download-cache data occupy three separate application-created Linux volumes. The session receipt binds their exact ownership labels, roles, daemon identity, non-root UID/GID, source archive and extracted content digest. Serialized metadata does not recreate authority.

`ExecutionService.prepareNativeDockerProject` requires explicit source consent and a host-authorized archive file matching the supported exact SHA-256. It verifies the already-present pinned image before creating new uniquely named volumes. A fixed one-time root operation assigns only those new mount roots to UID/GID 1000; extraction, configuration, acquisition and builds run as that non-root account. Existing volumes and workspaces are preserved. The archive is verified again inside the container, preserves native source links and is extracted with bounded path and content checks. The initial source-supported GRUB ISO profile uses its own separate output configuration.

`grantNativeDockerProject` verifies the native receipt and returns a distinct `docker-native` grant. `ExecutionService.start` admits only supported fixed targets for that grant, rechecks native source and volume identities, mounts source read-only and retains the existing owned-container lifecycle and cancellation proof. Firmware execution always uses `--network=none`, the pinned local image, dropped capabilities, no new privileges and finite CPU, memory, process, time and output limits.

Package-source acquisition is a separate explicit operation: `acquireNativeDockerCache` requires its own consent and runs the trusted Buildroot `source` target in an isolated network-enabled container. It never enables networking for firmware production. The selected configuration requires `BR2_DOWNLOAD_FORCE_CHECK_HASHES=y`; package archives must pass Buildroot's source hash checks. Source remains read-only, only the owned output/cache are writable, no ports or host credentials are passed, and acquisition receives its own recorded operation and cleanup verdict.

`inspectNativeDockerOutputs` rechecks the sealed source and returns size/SHA-256 records for fixed supported output names. A successful configuration or acquisition is not a full firmware build. Production needs an actual successful `all` result, verified owned-container cleanup and real output consumption. Image structure, boot and installation remain separate acceptance results.

This first backend profile is deliberately bounded. Ordinary host-path configuration editors, artifact viewers and persisted project descriptors do not silently reinterpret volume identifiers as paths. Dedicated renderer operations and those integrations require explicit wiring and verification before claiming native-volume GUI parity. Retain partial native volumes and their exact recovery identities when preparation or acquisition fails; never delete unrelated storage to create a successful result.
