# Host admission and preferences

The production entry is `src/main/index.cjs`. It opens only the packaged `dist/index.html`, with context isolation, renderer sandboxing and Node integration disabled. New windows, permissions, webviews and off-target navigation are denied. CSP disables network connections, frames, objects and external scripts. The preload exposes only bootstrap, typed requests, fixed window controls and validated operation-event subscription with idempotent listener removal. IPC admission requires the exact owned web contents, its top-level frame and the exact packaged URL.

The host owns the `desktop-owner` principal, `desktop-settings` namespace and settings database under the normal application-data profile. It grants only `settings.setLanguage`; callers cannot select another principal, directory or scope. Reload, renderer termination and window destruction revoke grants. Grants expire after one hour. Saving after expiry refreshes host bootstrap once and retries the same request only when the stored revision is unchanged. A stale revision retains the pending choice, reloads current settings and requires another explicit Save. A failed or unavailable save never reports success.

Language modes are `en`, `zh-HK` and `bilingual`; a fresh profile defaults to bilingual. Successful language changes reuse the strict parser, capability registry, durable SQLite transaction and reply/event translators. A successful operation emits only its exact recorded event; unrelated historical events are not replayed or labelled current. The operation reply is authoritative if event delivery is unavailable. Restart with a gracefully closed profile reads the saved language. Corrupt, foreign, locked or interrupted storage remains preserved and unavailable. The UI disables saving in that state. Crash recovery is not implemented.

Single-instance locking occurs before store creation. A second launch focuses the existing window. Graceful quit revokes authority and closes the database. Production stores are never replaced to make verification pass. An explicit `--verification-user-data=<absolute-directory>` launch argument selects a separate verification profile before initialization, without changing environment variables or the normal profile. It is intended for an owned fresh verification directory, not arbitrary existing user data. Runtime verification must record the exact source-bound executable and selected directory separately from production-default behavior.

System theme is the initial mode, with live light/dark choices for the current session only. That limitation is visible in Settings. Build version comes from the installed package; source and UTC build timestamp come from `dist/build-info.json`, written by the root build driver before packaging. Missing or malformed provenance displays Unavailable. The package no longer advertises an absent `runtime` resource directory; no execution adapters are implied.

Focused local tests cover sender/frame binding, request bounds and unknown commands, host namespace enforcement, expiry and reload revocation, durable replay and event deduplication, fixed window commands, exact event shape and listener cleanup. Existing broker tests cover graceful persistence and invalid-storage preservation. Type checking includes the renderer and typed bridge. Native packaged operation, actual bundled SQLite availability, language restart behavior and visual/keyboard evidence remain separate runtime acceptance work.
