# Standalone guest console design handoff

The booted operating system opens a compact local management console, never a marketing page. Python standard-library HTTP service binds only to 127.0.0.1:8766. Remote administration is intentionally unavailable. Workload publication is a separate, explicit operation, never automatic on boot or login.

## Workflow and states

1. Setup: a local console owner creates a password (minimum 12 characters). Setup is accepted only from the loopback client with an exact Origin and an ephemeral bootstrap CSRF value. Owner record uses PBKDF2-SHA256, random salt, persistent restrictive storage. Setup completion signs in and opens the workspace.
2. Locked: password sign-in, generic errors and bounded retry throttling. No private wording, workload details, credentials, or tunnel metadata are served before authentication. Sessions use memory-only bearer authorization, expire after 30 minutes, and are never stored as cookies or browser storage. Workload navigation receives no authorization value. Logout clears session and private DOM.
3. Workspace: left navigation for Workload, Remote access, and Settings. Workload card shows actual local health and an Open application action. Remote access has Off, temporary quick tunnel, and named tunnel selections. Starting requires healthy target and explicit confirmation that application authentication is configured. Locally managed named tunnel credential JSON arrives by bounded same-origin POST and is written mode 0600 below mode 0700 persistent storage. A generated local configuration fixes every ingress to the validated workload target. Remote connector tokens are rejected because remotely configured ingress cannot enforce that boundary. DNS routing remains an explicit separate setup action. Never echo credentials or return raw child logs.
4. Settings: English, Cantonese, bilingual; light/dark/system; local wording upload and clear. Optional image seed is loaded only after owner authentication. JSON mappings stay in the local browser cache, never remote APIs, logs or exports. The service offers the seed only to an authenticated loopback session. Invalid files preserve existing mappings.

The guest Vite configuration bundles every component locally into dist/appliance-guest; no compiled output is tracked. Bundle and runtime component verification remain pending. Normal viewport 1280x800; minimum 320 CSS pixels. Sidebar becomes a wrapping horizontal navigation below 640px. Content uses min-width:0, overflow-wrap:anywhere, responsive columns and no fixed-height text regions. ## Boundaries and pending evidence

Loopback HTTP protects local kiosk routing by interface isolation, Host/Origin checks and session/CSRF verification; it makes no LAN TLS claim. HTTPS generation for optional future LAN administration is deferred, not silently enabled with an untrusted certificate. Workload transport is independent and cloudflared terminates public HTTPS. Quick tunnels may publicly expose the workload, so a clear explicit public-access consent is mandatory and target authentication is an owner assertion, not a fabricated automated proof. Owner password recovery requires offline maintenance and is not an unauthenticated reset endpoint. No real-disk provisioning exists here.

Independent design review must precede implementation. Runtime boot, complete layout matrix, sound cues and universal feature parity remain unverified until separate real built evidence exists.

## Console workloads without HTTP

The producer may select mode console with an empty kioskUrl. The portal then retains owner/settings/wording workflows without inventing a target URL. It reports healthy=false and no HTTP proof, disables Open and tunnel activation, and offers explicitly labelled continuation without web verification. Completed setup records no-web separately from HTTP-response verification. Single-image container state comes only from a bounded docker inspect of the producer-owned material-workload name; Compose and unavailable inspection remain unknown/unavailable. Process-running is never HTTP or application-health proof.

## Protected workload owner enrollment

An optional producer-derived runtime.enrollment record contains exactly composeProject, service, volume, imageId, sourceRevision, productiveUrl and setupOrigin. The producer must derive these values from admitted prepared source, Compose and image receipts, never arbitrary renderer fields. The supported initializer service and logical volume are initialize and owner-config. Productive URL must equal the runtime workload URL. Missing or invalid metadata leaves enrollment unavailable.

The guest validates the unique Compose project/service container, immutable image ID, image OCI source revision, exact /run/owner named-volume mount, volume labels and mountpoint before reading only tls-cert.pem and setup-access-url. No owner record, database credential or TLS private key is read. Protected files must be bounded regular single-link files with restrictive permissions and stable identity. The TLS client uses only that public certificate, requires SAN hostname and validity verification, and compares the peer certificate with the exact admitted certificate. No global trust store or disabled certificate verification is used.

The local authenticated console starts an enrollment session. The backend reads the exact private one-time route, verifies its origin/path, retrieves the source form and validates its POST/input contract. Route and source CSRF remain session-bound backend memory for at most five minutes. The visible registered-control form submits username/password/confirmation through the existing console authentication and CSRF boundary; bounded URL-encoded forwarding reaches only that same verified private route. The source scripts/setup-host.py contract returns HTTP 200 only after save_owner succeeds; rejected validation or existing owner returns 400. Responses expose only readiness, saved state and a separate productive-health result. Routes, certificates, credentials and source form content never enter rendered output, history, diagnostics or exports. Login/logout invalidate pending enrollment.

Scoped productive health can be checked after enrollment. Productive browser navigation and public tunneling remain unavailable for this certificate-scoped profile because safe browser and tunnel-origin trust have not been integrated. The console labels this limit explicitly; it never claims a working productive kiosk from backend TLS proof. Other workload profiles retain their existing behavior.
