# Standalone appliance producer

The backend invokes `bash scripts/appliance/build-appliance.sh --spec /absolute/spec.json --output /absolute/output` as an unprivileged Linux user. WSL is the build environment only. The result contains its own x86-64 Linux kernel, initramfs, BusyBox init, Docker engine and legacy-BIOS GRUB bootloader. UEFI and hardware boot acceptance are not verified.

The producer fetches Buildroot 2025.02.6 from its official HTTPS download address and checks the source archive against the SHA-256 recorded in the entrypoint. Buildroot obtains its package sources using its normal source and hash rules. The selected Linux kernel is 6.12.47. Build dependencies must already be available to the unprivileged account; the producer reports missing tools without mutating the host. Compilation and detailed logs stay in a fresh Linux `/tmp` directory. `build-directory.txt` identifies that retained directory for recovery. Only the final ISO and manifest are copied to the selected output.

Build concurrency is fixed at two jobs. The verified Buildroot archive, package-source downloads and compiler cache are reused under the user's `material-buildroot-appliance` cache directory. Each production keeps its own output tree and overlay; cached downloads and compiler objects are not accepted as runtime evidence. The source archive is checked again before reuse.

Registry images are pulled for linux/amd64 and saved into the ISO. Archive inputs are loaded into the selected build environment's Docker daemon and inspected before saving. These staging actions can add images to that daemon, but never delete images or start workload containers on the build host. An image inventory records exact image IDs and registry digests. Compose inputs must use prebuilt image references. Builds, privileged containers, devices, extra capabilities, host PID/IPC namespaces, bind mounts and external configuration files are rejected rather than silently omitted. Host networking is allowed for discovery workloads such as Home Assistant. Preparing a source project into an appropriate image is a separate operation.

At boot, persistence requires an existing filesystem labelled `MATERIAL_DATA` on a separate disk. The appliance never partitions or formats a device. Without the required label it does not start its workload. With persistence disabled it uses volatile memory storage. Single-container workloads receive host networking and persistent `/config`; Compose named volumes use the Docker data root on the mounted data filesystem. Existing appliance containers are started again on subsequent boots. This is a container appliance, not a complete Home Assistant OS Supervisor installation.

Kiosk mode includes Weston, Mesa software/virtual GPU support and sandbox-enabled WPE/Cog. The browser opens the configured credential-free HTTP(S) URL. Browser startup, graphics drivers, LAN reachability, workload readiness and physical boot all require separate runtime verification.

Boot never activates a tunnel. The authenticated guest portal exclusively owns explicit activation, health checks and protected enrollment. Buildroot includes cloudflared 2025.1.0; named mode must use its supported credential-file route rather than assume newer token-file support. Account DNS routing and tunnel provisioning remain separate runtime checks.

An optional personal-wording JSON is bundled privately and mounted read-only at `/run/material/personal-vocabulary.json` for a single-container workload, with `PERSONAL_VOCABULARY_FILE` identifying that path. The workload must implement validation, local import and restoration itself. The producer does not inject scripts into arbitrary websites or claim that an unmodified workload applied the file. Compose workloads currently require their own explicit import integration. Any ISO carrying private wording or private container data must remain private.

`control-appliance.py --receipt /absolute/output/process.json --action status|cancel` checks the original Linux PID, process-group ID, start time and owner before signalling the isolated build process group. Identity mismatches are never treated as successful cancellation. A briefly unreaped process can return `running`; callers should use bounded status readback. Native launcher termination alone is not a cancellation receipt.

`manifest.json` is created only after Buildroot produces its ISO. It records the actual output path, bytes and streaming SHA-256. `bootVerified: false` deliberately distinguishes production from successful boot acceptance. No tests or source checks upgrade that value.

Image identity comparison distinguishes a classic configuration digest from a content-store manifest or index digest. [Moby v28.0.0's containerd inspection implementation](https://github.com/moby/moby/blob/v28.0.0/daemon/containerd/image_inspect.go#L92) returns the target descriptor digest as `Id`. This source reference explains supported representation differences; it does not establish which backend a particular host runs. Docker-save compatibility metadata remains required. When an OCI graph is present, the producer validates bounded descriptor sizes, blob digests, selected Linux configuration and compressed/uncompressed layer relationships before accepting a related manifest/index identity. Guest inventory records the configuration identity separately from the host engine identity. A graph that cannot bind the selected engine or registry source reports `SAVED_IMAGE_IDENTITY_MISMATCH`, without implying that the user changed the source. No relaxed digest equality or host security change substitutes for that proof.

The reviewed application-fork profile may provide owner-enrollment metadata to the authenticated guest portal. The producer requires the exact endpoint contract, productive URL, initializer image, named owner-volume mount and OCI source-revision label from the admitted workload. The emitted image identity is the saved configuration digest, not a desktop build revision or a host-specific manifest identifier. Missing, changed or ambiguous evidence leaves the enrollment field absent. The guest independently rechecks container and volume provenance before reading the public certificate and private setup-route file. This wiring does not itself prove successful enrollment, authorize a tunnel, disable TLS checks or install global trust.

Boot verification distinguishes a running container from an HTTP endpoint or Docker healthcheck that reports healthy. Only a loopback HTTP(S) target may provide endpoint proof. Console plans may omit that target, but then require a Docker healthcheck to prove workload readiness. Memory is derived from ISO size with a 4 GiB minimum and 32 GiB ceiling; verification fails before launch if available memory is insufficient. Its new sparse data filesystem is at least 16 GiB and grows with ISO size. These checks do not prove reboot persistence.
